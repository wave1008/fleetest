# テストクラスの作成

[in English](creating_testclass.md)

テストシナリオは、1つ以上の `@Test` メソッドを持つ `@TestClass` を記述した Swift ファイルです。
このページではファイルの置き場所と、最小限必要な形を説明します。

## ファイルの置き場所

`TestProjects/<プロジェクト>/scenarios/` 配下に `.swift` ファイルを置きます(サブフォルダも可。
例: `scenarios/Login/`)。`swift build`(または任意の `fleetest run`)を実行すると新しいファイルは
自動で発見されます。登録の手続きは不要です。

## 最小の例

```swift
import FTDSL

@TestClass                                      // 対象アプリは実行プロファイルが決める
class ログインテスト {

    @Test("正しいメールとパスワードでログインできる")
    func S0010() {
        scenario {
            scene(1, "ログインする") {
                condition {
                    launchApp()
                }.action {
                    type("#email", "test@example.com")
                    type("#password", account("[user1].password"))
                    tap("#login_btn||ログイン")
                }.expectation {
                    exist("#welcome_text||ようこそ")
                }
            }
        }
    }
}
```

値は `dataset/accounts.json` に置きます([テストデータ・アカウント](../commands/dataset_ja.md))。

- `import FTDSL` が必要です。
- `@TestClass` がクラスに付けるマーカーです。**`@TestClass` に `app:` は書けません** —— 対象アプリは
  実行プロファイル(アプリプロファイル → 実行中 platform の `ios.app`/`android.app`)から
  解決されます。これにより、同じシナリオを iOS と Android で別々の bundle ID のアプリに対して
  実行できます(プロファイルを使わない実行では `--app-id` で指定します)。`@TestClass(platform: "ios")`(または `"android"`)は、そのクラスが特定の OS
  でしか意味を持たないときだけ付けます。宣言した OS を回さない実行では、失敗ではなく
  skipped(対象外)として記録されます。
- `@Test("説明")` がテストメソッドに付けるマーカーです。**メソッド名は `S0010`、`S0020`、…**
  という **10 刻み**の命名慣習です(後から途中にステップを差し込んでもリネームが要りません)。
  レポート・`--scenario`・CI などで使われるシナリオ ID は `クラス名.メソッド名` です。
- 本体は `scenario { scene(n, "題") { condition { }.action { }.expectation { } } }` の形です
  —— 各ブロックの意味とチェーンの仕方は[コードの構造](./testcode_structure_ja.md)を参照してください。
- コマンド(`tap`、`type`、`exist` など)は**同期・非 throw の自由関数**です。`try`/`await`
  もクロージャ引数(`{ it in }`)も不要で、暗黙にカレントの実行コンテキストへ作用します。

## beforeEach / afterEach

```swift
@TestClass
class ログインテスト {
    func beforeEach() {
        irregularHandler("#promo_modal", dismiss: "#btn_promo_close")
    }
    func afterEach() {
        // 失敗しても必ず走らせたい後処理
    }

    @Test("...")
    func S0010() { scenario { /* ... */ } }
}
```

`beforeEach()` と `afterEach()` は、クラス内の各 `@Test` の前後で自動実行されます。
**`afterEach()` は失敗後でも実行される**ため、シナリオが途中で中断してもスキップされては
困る後処理をここに置きます。

`func beforeAll()`(任意)は、**1回の run × 1クラスで1回だけ**(マシンをまたぐ run ではマシンごとに1回)、そのクラスのどのシナリオよりも前に
(どのデバイスでも)自動実行されます。run 全体で共有する準備(テストデータの作成と、できた値の `writeMemo` など。
[メモ](../commands/memo_ja.md))に使います。そのクラスのシナリオを受け取った他のデバイスは終わるまで待ちます。
失敗すると、その run のそのクラスの残りのシナリオは実行されずに失敗として記録されます。

`func afterAll()`(任意)は、**1回の run × 1クラスで1回だけ**(マシンをまたぐ run ではマシンごとに1回)、run の全デバイスの仕事が終わった後に
専用のプロセスで自動実行されます。`beforeAll()` で作ったテストデータの削除のような、run 全体の片付けに使います。
`beforeAll()` の成否に関わらず走り、メモを読めます。中断した run では走りません。

`func setUpDevice()`(任意)は、**1回の run × 1デバイス × 1クラスで高々1回**、そのデバイスに
配られたそのクラスの最初のシナリオの `beforeEach()` の前に自動実行されます。テストごとに繰り返したく
ない、デバイスごとに必要な準備(アプリの言語切り替えなど)に使います。シナリオは1本ずつ別プロセスなので、ここで設定した
インスタンスのプロパティはその最初のシナリオからしか見えません。`setUpDevice()` ではメモに書けません(読むだけです)。
値の受け渡しは `beforeAll()` で書いてください([メモ](../commands/memo_ja.md))。

`func tearDownDevice()`(任意)は、**そのデバイスがその run のシナリオをすべて終えた後**に、そのデバイスで
そのクラスのシナリオが1本でも走っていれば**1回だけ**自動実行されます。`setUpDevice()` で用意したものの片付けに
使います(`setUpDevice()` が失敗していても走ります)。デバイスが途中で使えなくなった場合や、run を中断した場合は
走りません。結果は run のログとレポートに残りますが、テストの合否には数えません。

## クラスのテストを1か所で・順番に流す(@RunOnSingleMachine / @RunOnSingleDevice / @RunInOrder)

既定では、クラスのテストは run のデバイス(複数のマシンにまたがることもあります)へ分かれて並列に走り、順番も決まっていません。
テストが互いに独立していれば、これが最も速く、何も付ける必要はありません。**どうしても必要なときだけ**、クラスに次のどれか1つを付けます
(`@TestClass` とは別の行に書きます。理由の文(例: `@RunInOrder("注文の流れ")`)は3つとも省略できます)。

```swift
@RunInOrder("注文の流れ")
@TestClass
class 注文フロー {
    @Test("カートに入れる")
    @Order(10)
    func S0010() { scenario { /* ... */ } }

    @Test("注文を確定する")
    @Order(20)
    func S0020() { scenario { /* ... */ } }

    @Test("注文履歴に出る")
    @Order(30)
    func S0030() { scenario { /* ... */ } }
}
```

| | `@RunOnSingleMachine` | `@RunOnSingleDevice` | `@RunInOrder` |
|---|---|---|---|
| 流す場所 | 1台のマシン | 1台のデバイス | 1台のデバイス |
| クラスの中 | 並列(そのマシンのデバイスへ分かれる) | 1本ずつ。他のクラスを挟まない | 1本ずつ。他のクラスを挟まない |
| 順番 | 決まっていない | 決まっていない(順番に頼れない) | `@Order` の順(保証される) |
| 失敗の後 | 続ける | 続ける | 残りは実行されず、失敗として記録される |
| `--failed` | 落ちたテストだけ | 落ちたテストだけ | クラスの最初から |

- **`@RunOnSingleMachine`** は、クラスのテストをすべて同じマシンに寄せます。別のマシンのテストからは、`beforeAll()` で作ったデータも
  メモも、そのマシンの compose.yaml のサーバーのデータも見えません。同じものを見せたいクラス(例: `beforeAll()` が compose.yaml の
  サーバーに作ったデータを全テストが読む)に付けます。マシンの間で負荷を分けられなくなります。1台のマシンだけで回すなら効果はありません。
- **`@RunOnSingleDevice`** は、クラスのテストを1台のデバイスで1本ずつ流します。そのクラスの並列が無くなるので、同時に走るとぶつかるテストだけに使います。
  **まず別のアカウントで分けられないかを考え、分けられないときに付けます**(例: サーバー全体の設定を切り替えるテストなど、アカウントで分けられない共有のもの)。
  順番は決まっていません(テストどうしが結果に頼ってはいけません)。防げるのは**そのクラスの中の**同時実行だけで、
  同じアカウントを別のクラスも使えばぶつかります(シナリオごとに別のアカウントを使ってください)。
- **`@RunInOrder`** は、1台のデバイスで `@Order` の順に流します。並列化を妨げ、途中で失敗すると残りは実行されず、
  再テストもクラスの最初からになります。必要な場合だけ使ってください。**まず、1つの `@Test` にまとめられないかを考えます**。

この例のような流れは、ふつうは1つの `@Test` にまとめます。分けるのは、長すぎて途中の失敗を分けて見たいときなどです。

`@Order(n)` は `@Test` のメソッドに付ける順番です。`@RunInOrder` のクラスでは**すべての `@Test` に必須**で、値は整数です
(10, 20, 30 のように飛び番でかまいません)。同じクラスで同じ値は使えません。`@RunInOrder` の無いクラスに付けるとコンパイルエラーです。

寄せる先(どのマシン・デバイスか)はコードに書けません。クラスの最初の1本を受け取ったマシン・デバイスに寄ります。複数のマシンに分かれる run では、寄せた先が実行ログに1行出ます。
デバイスに寄せた(`@RunOnSingleDevice` / `@RunInOrder`)クラスのデバイスが途中で切れたら、復帰を待ってそのテストを流し直します。
復帰できなかったときは、残りのテストを他のデバイスへ移さず失敗として記録します。

**エラーになる場合**

- 3つの属性を2つ以上同時に付けた、または `@TestClass` の無いクラスや `@Test` のメソッドに付けた(コンパイルエラー)。
- `@Order` を `@RunInOrder` の無いクラスで使った、`@RunInOrder` のクラスに `@Order` の無い `@Test` がある、`@Order` の値が重複している(コンパイルエラー)。
  `@Order` を `@Test` の無いメソッドやメソッド以外に付けた場合もコンパイルエラーです。`@Draft` / `@Deleted` のテストにも `@Order` は要り、実行からは外れ、「先頭から連続」はそれを除いた並びで数えます。
- `@RunOnSingleDevice` / `@RunInOrder` のクラスで、テストの OS の宣言(`@TestClass(platform:)` / `@Test(platform:)`)がそろっていない
  (全部が未宣言か、全部が同じ OS でなければなりません。コンパイルエラー)。`@Test(platform: nil)` は書かないのと同じ扱いです。
- `@RunInOrder` のクラスを、クラス全体か先頭から連続した範囲以外の形で選んだ(`--scenario` で途中の1本だけを流す、拡張の木からの途中の1本のデバッグ実行、など。run の開始時に断られます)。
  途中のテストを確かめるときは、クラスごと流します。書きかけの後ろのテストには `@Draft` を付けておきます。
- [レスポンス計測](../running/response_measurement_ja.md)の run に `@RunInOrder` のクラスがある(run の開始時に断られます)。
- 両方の OS のテストを持つ `@RunOnSingleMachine` のクラスで、両方の OS のデバイスを持つマシンが無い(run の開始時に断られます。
  `@TestClass(platform:)` でクラスを OS ごとに分けるか、1台のマシンに両方の OS のデバイスをそろえます)。

`--broadcast` と、複数のマシンで同じものを流す実行(`--split` の無い `--fleet`。[リモート実行](../../fleet/remote_runners_ja.md)参照)では、この属性は効きません(クラスが複数のデバイス・マシンで走ります)。
`--broadcast` ではそのことを示す1行が出ます。`--fleet` では出ません。
テストデータの置き方は[テストデータの置き方](../writing/test_data_placement_ja.md)、メモの共有は[メモ](../commands/memo_ja.md)を参照してください。

## 未完成・廃止のマーク

- `@Draft("理由")` は未完成(実装中)であることを示すマークです。一覧には「作業中」として
  残りますが、全実行・フォルダ実行・クラス名指定の一括実行からは除外されます(完全一致 ID
  の明示指定では実行できます)。
- `@Deleted("理由")` は論理削除であることを示す同種のマークです(一括実行から除外・完全一致
  ID では実行可)。コードはファイルに残るので、アノテーションを外すだけで復活します。

どちらもクラス、あるいは個々の `@Test` メソッドに付けられます。

## 注意点

- `@RunOnSingleMachine` はマシン間で負荷を分けられなくなります。`beforeAll()` やデータを1つにまとめたいときだけ使い、寄せる先はコードに書けません(最初の1本を受け取ったマシンに寄ります)。
- `@RunOnSingleDevice` はそのクラスの並列が無くなり、順番も決まっていません。防げるのはそのクラスの中の同時実行だけで、同じアカウントを別のクラスも使えばぶつかります。
- `@RunInOrder` は並列化を妨げ、失敗すると残りは実行されず、再テストもクラスの最初からになります。まず1つの `@Test` にまとめられないかを考え、`@Order` は全テストに必須(整数・重複不可)で、選べるのはクラス全体か先頭から連続した範囲だけです。

## DR-90 サービス(compose)の枠はアプリをビルドせず成果物を受け取る

- 種別: 方針
- 決定: ユーザー 2026-10-14
- 内容: アプリはビルドしない。成果物を受け取る。URL から成果物を取ってくる機能も作らない
- 理由: CMP / RN の iOS は Xcode が要るので Linux コンテナで動かず、Seatbelt の中では SwiftPM / xcodebuild の入れ子のサンドボックスで落ちる(SB-2.8。xcodebuild は未実測)。ビルドは clone したコードの実行そのもので、通信・`~/.gradle`・常駐デーモンまで開けると枠が残らない。URL 取得は取得元の検査が別に要る
- 根拠: SB-2.8
- 見直す条件: 未記録
- 参照元: docs/remote-runner/17.md(RR-17「決めたこと」)

## DR-91 サービスのサーバーはコンテナに限る

- 種別: 方針
- 決定: ユーザー 2026-10-14
- 内容: ホストで直接動くサーバー(`npm start` 等)は対象外。ランタイムは Docker と Apple Container の両方で、書くのはどちらでも同じ `compose.yaml`
- 理由: 枠の中から常駐プロセスを残させない(保証ではなく目標。離脱した子孫は検出できないこともある)
- 見直す条件: 未記録
- 参照元: docs/remote-runner/17.md(RR-17「決めたこと」)

## DR-92 名前付きボリュームは run をまたいで既定で残す

- 種別: 方針
- 決定: ユーザー 2026-10-14
- 内容: 名前付きボリュームもプロジェクトの接頭辞で名付け、既定は残す。片付け(正常系・孤児の回収)はコンテナとネットワークだけを消す。全部を消すのは人が打つ `fleetest services reset`。前の run の変更は run-setup.sh で戻す
- 理由: 巨大なテストデータの読み込みを run ごとに払わない。残すことの注意は、run の順序に依存する失敗が出やすいことと、ランナー機ごとに別の DB になること(どちらも run-setup.sh で毎回そろえれば防げる)
- 見直す条件: 未記録
- 参照元: docs/remote-runner/17.md(RR-17 のボリュームの節)

## DR-93 実機(物理端末)でもサービスを使ったテストをできるようにする

- 種別: 実測
- 決定: ユーザー 2026-10-14
- 内容: 方式は推奨の (b)+(c)。(c) Android の実機は親が `adb reverse` を代行する。(b) iOS の実機と Android 実機の UDP はマシン側設定の `services.publishForPhysicalDevices` で名指しした LAN アドレスで公開する。iOS 実機のレーンを含む run は1機械に限る
- 理由: iPhone の実機から Mac の `127.0.0.1` には届かない(端末自身)ので、経路が要る
- 根拠: 同日の実機での実測(iPhone SE3・Pixel 4a・LAN の対向は M1Ultra。ファイアウォールは ON のまま)
- 見直す条件: 未記録
- 参照元: docs/remote-runner/17.md(RR-17 の実機の節)

## DR-94 UDP・TCP の確認用中継のイメージは公式の `alpine` を digest で固定し、`socat` を入れて手元でビルドする

- 理由: 第三者のイメージ(`alpine/socat`)を digest で固定するだけの案より信頼の置き場が少ない
- 見直す条件: 未記録

## DR-95 サーバーのイメージは完成したものを受け取るのを基本にし、ビルドはマシン側で名指ししたビルド元だけ許す

- 種別: 方針
- 決定: ユーザー 2026-10-14
- 内容: 基本は CI でビルドしたイメージ(`image:` またはアーカイブ)を受け取る。開発用に、マシン側の `services.buildSources`(読み取り専用)に書いたビルド元からのビルドだけ許す。「`scripts/` にソースを置く」は勧めない
- 理由: clone したコードを fleetest の Mac で実行しない(アプリと同じ考え方)。開発用のビルド元はサーバーを直しながら試すとき CI を待たないため
- 見直す条件: 未記録
- 参照元: docs/remote-runner/17.md(RR-17「サーバーのイメージの用意」)

## DR-96 UDP の経路を run の前に確かめ、届かなければ run を始めない

- 種別: 実測
- 決定: ユーザー 2026-10-14(確認の導入)・2026-10-15(届かなければ run を始めない)
- 内容: UDP を宣言した compose だけ、Mac の `127.0.0.1` → ランタイムの公開 → コンテナの経路に親がトークンを送って確かめる(1 s × 3 回)。3回届かなければ `ServicesError`(phase wait)で run を始めない。確かめるのは経路だけで、利用者のサービス自身は確かめない
- 理由: 確かめないと、ランタイムが UDP を運ばないとき(`docker port` の表示は正常でエラーも出ない)テストが原因の見えないタイムアウトで落ち、アプリの不具合に見える
- 根拠: Apple は 3 回の probe で必ず応答・Rancher の SSH 転送方式は 3 回とも届かない(費用は Apple 1〜2 s / run・Docker 約 0.3 s / run・UDP を宣言しない compose では 0)
- 見直す条件: 未記録
- 参照元: docs/remote-runner/17.md(RR-17 の UDP の経路の確認)

## DR-97 1マシンで同時に走る run は1本

- 種別: 方針
- 決定: ユーザー 2026-09-21
- 内容: 「1つのマシンで同時に複数の run を実行することは想定していない」。`dispatch.lock` は `~/.fleetest/` に1本で、リモートのディスパッチもローカル run も同じロックを取る。避けたい副作用ではなく守りたい不変条件で、ツールが構造的に守る
- 理由: 高負荷になりすぎてテストが不安定になる。手元の run が取らないと、他人がその Mac をランナーとして登録しているとき、他人のディスパッチと同時に走ってデバイスとポートを奪い合う
- 見直す条件: 未記録
- 参照元: RR-13(docs/remote-runner/13.md)・.claude/rules/remote.md「1マシンで同時に走る run は1本」

## DR-98 `remote unlock --force` は持ち主・生死を問わずロックを外し、生死の確認はしない

- 種別: 方針
- 決定: ユーザー 2026-10-03
- 内容: `RemoteDispatchUnlock.decideForced`。外した相手と取得時刻を出力に残す。止まっていると人が確かめたときだけ使う
- 理由: 奪う手段が `run --force-lock` にしか無いと、run を伴わない操作(align)では他人の止まったロックを外せず ssh で直接消すしかない。生死の確認は他人の Mac の pid がランナーから見えず、ランナー上の pgrep も転送・ビルド中のディスパッチを見逃すので、確かめた体裁を作らない
- 見直す条件: 未記録
- 参照元: RR-13(docs/remote-runner/13.md)

## DR-101 ToolchainFingerprint は製品版が同じで build 番号だけ違うときディスパッチを止めない(advisory)

- 種別: 方針
- 決定: ユーザー(日付未記録)
- 内容: 製品版(`Xcode X.Y`)が同じで build 番号だけ違う(ベータの seed 違い)は advisory として止めない。製品版が違う(26 vs 27 等)は従来どおり fail-closed。仕分けは `RemoteCompat.verdict` の1箇所

## DR-102 ランナーの Xcode はディスパッチが発行側に合わせて `DEVELOPER_DIR` で自動選択する

- 種別: 方針
- 決定: ユーザー(日付未記録)
- 内容: 選択は `DEVELOPER_DIR`(プロセス単位・sudo 不要)。`xcode-select -s` は使わない。候補はランナーの `/Applications` 直下の `Xcode*.app` だけ。一致0個・複数は候補一覧を出して拒否し、手近な Xcode へ黙って倒さない

## DR-103 マシン間の割り振りは、空いたデバイスが親から次のシナリオを1本ずつもらう形(案 A)

- 種別: 実測
- 決定: ユーザー 2026-10-27
- 内容: 最初に決め打ちする割り振り(LPT)をやめる。空いたデバイスに、今渡したときの終わる時刻が、同じ platform の他のレーンに回したときの一番早く終わる時刻以下のシナリオだけを渡す。比べるときは他のレーンに控えている分も数える(`FTCore.BacklogPlacement`)。1本も積まれなければ何も渡さず待たせる
- 理由: 初回(記録なし = 均等割りで最大 134 秒遊んだ)・短い run(最大 23〜32 秒)・所要のばらつきが大きい run の遊びを消す。1本ずつ他のレーンの次の空きとだけ比べると、速いレーンの控えの山を前に遅いレーンが待ち続ける。遅いマシンが終わり際に長いシナリオを取って全体を引き延ばさない
- 根拠: PT-8.1
- 見直す条件: 未記録
- 参照元: RR-8.1(docs/remote-runner/01-11.md)

## DR-112 デバイスの同時起動は最大2台の固定にし、1台ずつ完結させる

- 種別: 実測
- 決定: ユーザー 2026-07-16(Simulator の同時起動の枠は日付未記録)
- 内容: ワーカーは1台を「ブート →(iOS)ブリッジ供給」まで完結させてから次へ進む。「同時進行が2台を超えて見えない」こと自体が要件。供給バッチ化(ProvisionBatcher)と、cores/3 への同時数の自動スケールは実装後に撤回した。Simulator の起動は機械全体(プロセス・クローンをまたぐ flock)で Shutdown → Booted を同時2台まで。設定の口は置かない
- 理由: 供給バッチ化は demo-3x3 コールドで 138s→79s と速かったが、供給中とブート中のデバイスが同時に3〜4台進行して見えるため撤回した。Simulator は5台の一斉起動で空きメモリが尽きて FM が死んだ(MN-97)
- 根拠: PT-3.3・MN-97
- 見直す条件: 未記録
- 参照元: PT-3.3・docs/performance-tuning/guide.md の `maxConcurrent` と Simulator の同時起動の枠の行

## DR-115 OCR を run ごとの補助プロセス(`fleetest api vision-serve`)へ移さない

- 種別: 実測
- 決定: ユーザー 2026-10-08

## DR-180 改名にも欄の追加にも互換措置(別名・旧キーの読み替え・欠落の既定値)を置かない

- 種別: 方針
- 決定: ユーザー 2026-09-08(改名)・2026-09-20(欄の追加)。2026-11-14 に、ベータ版として公開中でも保つと確認
- 内容: CLI のオプション名・サブコマンド名・JSON キーを直すとき、旧名の別名・非推奨の記録・移行案内を置かず、呼び出し元(拡張・Scripts・docs・スキル)を同じコミットで全部追随させる。旧キーの読み替え(`decodeIfPresent(.oldKey)` の逃げ道)も足さない。欄を足すときは必須にして版を +1 する(DR-5 はこのうち API の JSON 契約の部分)。変更点はリリースノートで伝える。例外は利用者のプロファイルの JSON にある旧キーで、既存の読み替えを勝手に消さない(利用者の資産)

- 参照元: CLAUDE.md「版と契約の同期」・DR-5

## DR-181 スコープ(`>>`)は木の親子だけで判定し、中身を持たない容器を矩形で補わない

- 種別: 実測
- 決定: ユーザー 2026-11-16(おすすめを採用)
- 内容: スコープの中身は木の子孫だけ。iOS の Compose Multiplatform が `testTag` だけの Row/Column を子の無い葉で出し中身を兄弟へ繰り上げる形(FD-1.4)でも、矩形の包含で中身を補わない。代わりに「見つからない」の失敗文で「容器は木にあるが中身を持たない」事実と書き方(一意な `#id`・ラベル・相対セレクタ)を言う(`LocatorResolver.childlessScopeContainer`。DSL と MCP で共有)。`>>` 自体は残す(効かないときは赤 = 誤った緑を作らない・容器の中で数える序数の手段・Shirates 準拠)
- 理由: 利用者の提案(子孫の無い容器だけ、同じ親の下で中心が矩形に入る要素を中身とみなす)を実装して 402 枚の木(E2E・E2EX・E2EY・sut-ec-mobile の両 OS 350 枚 + 実アプリのコーパス 52 枚)に当て、もう片方の OS の木の子孫と突き合わせた。全フレームワークに効かせると、無関係な重なり(下部タブとその下のホームの行・固定ボタンと WebView の行・カレンダーの隣の日・地図のピン・画面を覆うツールバー)を中身として拾う誤りが正しい例より多かった。iOS の Compose・容器の型 `other` に絞っても 20 件中 1 件(E2EY の隠れるバーが裏の一覧の行を拾う)が残り、木の材料では見分けられない。「効かなければ赤」を「たまに誤って緑」に変える取引で、材料の無い所を幾何で埋める直し(MN-108)と同じ型
- 見直す条件: ブリッジが Compose の semantics の親子(AX の外の情報)を木へ載せられるようになったとき。または、矩形で補う形の誤りを見分ける材料が木に入ったとき(同じ 402 枚で誤り 0 を示してから)
- 参照元: docs/commands.md「容器のスコープの無い序数」・docs/framework-differences.md FD-1.4

## DR-182 利用者向けの日本語の面では、テストの現場で一般的な語を使う(内輪の語を置かない)

- 種別: 方針
- 決定: ユーザー 2026-11-16(書籍の著者からの提案を採用)
- 内容: docs/user-docs の `_ja.md`・手本シナリオ(TestProjects/sut-ec-mobile)のコメントと scene の題・拡張の日本語 UI 文字列では、木 → (アクセシビリティ)ツリー・掴む → 取得する/見つかる・容器 → コンテナ・撃つ → 実行する/再試行する・振り直し → 再実行・払う → スワイプ(flick はフリック)・起こす → 起動する・指紋 → フィンガープリント・画素 → ピクセル・見本 → テンプレート画像/学習用画像・折り返しの下 → 画面外・関門 → ゲート・配布口 → 配布元・(マクロの)印 → 〜を示すマクロ・後始末 → 後処理・基準化 → 初期化・擬陽性 → 偽の成功 と書く。`UserFacingSpellingTests` が user-docs の日本語と i18n の再混入を落とす。デバイスの「凍結」(端末が固まる事象)と「整定」は fleetest の概念として定義済みなので残す

- 参照元: Tests/FTCoreTests/UserFacingSpellingTests.swift

## DR-185 iOS の `hideKeyboard` は、焦点の欄が複数行なら Enter を送らない(取り消した)

- 種別: 方針
- 決定: ユーザー 2026-11-16(おすすめを採用)。同日、前提が崩れたので取り消した(0.22.1 に入り、0.22.2 で戻す)
- 内容: 取り消した。今は DR-27 のとおり、何もない点のタップで閉じなければ Enter を送る。取り消した形は「焦点の欄の型が `textView` なら Enter を送らずに失敗する」だった
- 理由: 前提の「`textView` = 複数行の欄」が成り立たなかった。iOS の Compose Multiplatform は1行の欄(`singleLine = true`)も `textView` で出す(E2E-CMP の `#field_single`・`#field_password`、sut-ec-mobile の住所フォームの欄)。sut-ec-mobile の住所フォームは背景のタップで閉じず Enter で閉じる欄で、0.22.1 ではそこで `hideKeyboard()` が失敗した(書籍の著者が報告)。型では1行と複数行を見分けられない
- 見直す条件: 複数行の欄かを木やブリッジの申告から事実として言える材料が取れたとき(OI-245)
- 参照元: docs/open-issues.md の OI-245・FD-2.5

## DR-186 Android の座標ドラッグは gRPC ではなくブリッジの `/gesture` で撃つ(DR-73 を狭める)

- 種別: 実測
- 決定: ユーザー 2026-11-16(おすすめを採用)
- 内容: `swipeBy`・`swipePointToPoint`・`swipeElementToElement`・探索の寄せ・空打ちの座標ドラッグ(`AndroidDriver.drag`)を、Emulator でも実機でもブリッジの `/gesture`(1本指)で撃つ。ブリッジは出来事に予定の時刻(開始 + t)を付ける。短くて遅いドラッグの最初の区間を速める計画(OI-168 ⑥)は途中の1点として渡す。長押し・キーなどほかの Emulator の操作は DR-73 のまま gRPC
- 理由: gRPC はホストから指の出来事を実時間で送るので、ホストの負荷で払いが伸びて離す直前の速さが落ち、速さで決める部品(払って消す・フリック)が戻った(E2EX-Android の行を払って消すシナリオ: 0.3 秒の払いが 0.51 秒に伸びた回だけ赤)。同じ負荷で gRPC 80 回中 3 回赤・ブリッジ 0 回。DR-73 の理由だった速さは、払いの手順の所要が中央値 0.95 秒対 0.86 秒でブリッジの方が遅くならない(回転の読み取りが要らない)
- 見直す条件: ブリッジの経路の所要が gRPC より目に見えて遅くなったとき・ブリッジの /gesture で撃てない操作が見つかったとき
- 参照元: AndroidDriver.drag・DS-16


## DR-187 iPad のキーボードの閉じるキーを押す口をブリッジに足さない(横向きの iPad の WebView は据え置き)

- 種別: 方針
- 決定: ユーザー 2026-11-17(おすすめを採用)
- 内容: XCUITest ブリッジはキーボードの部分木をキーごと木から落とす(`BridgeRouter+Snapshot.gather`)ままにし、iPad のキーボードの閉じるキーを押す口を足さない。WKWebView の欄に焦点があるとき iOS の `hideKeyboard` とキーボードの下の対象への tap が閉じられずに赤になる形は据え置く(縦向きで書けば避けられる)
- 理由: 外側のタップでも Enter でも WKWebView の欄は焦点を失わず、副作用の無い閉じ方は閉じるキーだけ。足すにはブリッジの変更(版上げ・全端末のランナーの作り直し・xcuitest モードの確認)とキーの見分け方(言語に依らない印)の実測が要り、影響(横向きの iPad の WebView だけ)に対して費用が大きい
- 見直す条件: 横向きの iPad の WebView の利用者から要望が出たとき・別の画面でも閉じるキーでしか閉じられない形が見つかったとき
- 参照元: docs/open-issues.md の OI-253

## DR-188 救済の送りの後も対象が座標のクランプされた残骸のままなら、撃たずに失敗にする

- 種別: 方針
- 決定: ユーザー 2026-11-18(おすすめを採用)
- 内容: tap 等の触る操作で、掴んだ要素が送り残し(容器の外)のまま救済の送りを終え、しかも座標がクランプされた残骸(同じ点に中身のある要素が積み重なっている = 注記の stacked と同じ `OcclusionGeometry.stackedRefs`)なら、その座標を撃たずに `notFound` で失敗し「送って描かれてから押す」と案内する。容器の外でも座標が壊れていない要素は従来どおり警告付きで撃つ
- 理由: クランプされた座標には別の物が描かれていると分かっている。撃つと別の画面が開いて ✅ になり、次の操作が失敗するまで気付けない(iOS 連絡先の編集フォーム・XCUITest の木で実測。inapp-boost では正しく届いた)。Android の同じ状況(送った後に画面から外れた)は既に「何も触っていない」で失敗にしていた
- 見直す条件: クランプの残骸の判定が描かれている要素を誤って残骸と読む実例が出たとき
- 参照元: StepExecutor+Actions.swift の送り残しの処理

## DR-189 スクロール探索の逆走査は開始位置より先を探さない

- 種別: 方針
- 決定: ユーザー 2026-11-18(おすすめを採用)
- 内容: 指定の向きに送り切って見つからなかったときの逆走査(飛び越しの救済)は、送る前の木にあった `#id` の要素が開始位置を越えて戻った時点で止め、越えた帯(送る前の画面より向こう)で見つけた物は採らない。共通の `#id` が無く越えたか測れないときは従来どおり反対の端まで戻る
- 理由: 逆走査は飛び越した分の救済で、指定と逆の向きを探す機能ではない(「指定の向きだけを探す」2026-10-29 の決定と揃える)。開始位置より上にあった行を inapp-boost だけが見つけ、xcuitest(容器が木に出ず逆走査しない)と合否が割れ、作成中の確認で誤った欠陥が起票された(SUT Store の iOS・並べ替えの後)
- 見直す条件: 開始位置の判定(共通の `#id` の変位)が、整定の揺れや並び替えで誤って「越えた」と読む実例が出たとき
- 参照元: StepExecutor+Settle.swift の `reverseSweep`

## DR-190 id の無い横のコンテナへ届かせるために、木の行の形から横の帯を推定しない(今は払い直し先を絞るだけ)

- 種別: 方針
- 決定: ユーザー 2026-11-18(おすすめを採用)
- 内容: 横の探索の払い直し先(`ContainerGeometry.uniqueScrollContainer`)は、横の向きを申告するか子が横に並ぶ容器だけを数える。並びの決まらない容器(全画面の縦の本体)は数えない。id が無く木にも容器として出ない横のコンテナは名指せない制約として docs に書き、アプリ側で `#id` を付けてもらう。木の行の形(同じ y の押せる要素が並び、端が切れている)から帯を推定する案と、`scrollFrame` に名指した要素の帯を固定して消えても止めない案は採らない
- 理由: 行の形からの推定は固定のタブ・セグメントと見分けられるかが未測定で、材料の無い所を形で埋める直し(MN-108・DR-3)になる。帯を固定する案は「容器が木から消えたら失敗」の仕様を変える。払い直し先を絞れば、届かないことは変わらないが、全画面の容器を払う空振りと誤った名指しは消える
- 見直す条件: 反例の形を固定コーパスと SUT で見分けられると測れたとき・横の容器を木へ載せる材料(ブリッジの申告)が入ったとき
- 参照元: ContainerGeometry.swift・docs/user-docs/reference/writing/ui_component_patterns(_ja).md「横に送るコンテナは scrollFrame を必ず渡す」

## DR-191 ブリッジの供給の排他(provision.lock)の待ちは、見込みを言わず経過だけを一定の間隔で言う

- 種別: 方針
- 決定: ユーザー 2026-11-18(おすすめを採用)
- 内容: 別のプロセスが provision.lock を持っている間、待ち始めに1行、その後 30 秒ごとに経過の1行を出す。残り時間の見込みは出さない
- 理由: 相手の供給があと何台・何秒かかるかはこのプロセスには分からない(推測で言わない = DR-4)。経過が出れば止まっていないことは伝わる(実測の待ちは 150〜180 秒で、待ち始めの1行の後は無言だった)
- 見直す条件: 相手の供給の進み具合を読める材料(台帳)が入ったとき
- 参照元: BridgeProvisioner.swift の `ProvisionLock.acquire`

## DR-194 run が引き取った `services up` のサーバーは、run の片付けの後に同じ指定で起こし直す

- 決定: ユーザー 2026-11-18(おすすめを採用)

## DR-195 キーボードの下の対象への MCP の ref 操作(tap・type・clear・長押し)は、副作用なしで閉じてから撃つ(DR-41 を狭める)

- 種別: 方針
- 決定: ユーザー 2026-11-18(おすすめを採用)
- 内容: 中心がソフトキーボードの下にある要素への ref の操作は、`ft_hide_keyboard` と同じ閉じ方(Enter を送らない)で閉じてから引き直して撃つ。閉じられなかった・閉じても下のままなら従来どおり断る(DR-41)。ref で始点を指すジェスチャ(drag・pinch・ダブルタップ)は従来どおり断る
- 理由: DSL の tap は閉じてから撃つので、MCP だけ断ると、MCP では届かないが DSL では届くという差が docs に無いまま AI を迷わせた(Pixel 4a・sutstore_and・e2ey_rn_4a)。人が操作できることはツールが最善を尽くす方針。キーを押してしまう害(DR-41 の理由)は閉じてから撃つので起きない
- 見直す条件: 閉じる操作が欄の確定など副作用を起こす実例が出たとき
- 参照元: MCPServer+GesturesTools.swift の `refAfterClosingKeyboard`・docs/user-docs/reference/tools/mcp_server(_ja).md「シナリオに写すときの違い」

## DR-196 MCP の作成中の確認は可視性検証なしのまま、スキルは完了の前に本番と同じ経路で回すことを必須にする

- 理由: マシンをまたぐ run では `beforeAll()`・メモ・compose.yaml の DB がマシンごとに分かれ、マシンの中でもクラスのテストは並列に・LPT の順で走るので、
  「データを1つにまとめたい」「同時に走るとぶつかる」「順番に依存する」の3つの要求をシナリオの側から言う口が無かった。`@TestClass` の引数にせず
  独立した属性にしたのは、意味ごとに分かれて読みやすく、属性ごとに引数を足せるため。名前は効果を言う(`Resource` を含む名前は排他と読まれるので採らない)。
  同時付与をエラーにしたのは、付いている属性から挙動が1つに決まるようにするため。`@Order` を `@RunInOrder` の外で受け入れないのは、並列に走るクラスで
  守られない順番を書けてしまうため(付けただけで自動で直列にする形は、習慣で付けたクラスを黙って遅くするので採らない)。`@Order` を必須にしたのは、
  関数名の順(文字列の比較)が `test10` < `test2` になり日本語名では予想できないため。`@RunOnSingleDevice` の順番を決めないのは、保証の無い決まった順に
  利用者が気づかず頼るのを避けるため。OS が混ざったクラスをデバイスの属性で断るのは、OS ごとに別のデバイスで同時に走り、順番も「同時に走らせない」も守れないため(未宣言と明示の組も断るのは、
  run の既定の OS しだいで結果が変わる形を作らないため)。離脱したデバイスの残りを移さないのは、走っていたテストの流し直しと残りが2台で同時に走りうるため。
  docs の趣旨: どれも並列を犠牲にするので必要な場合だけ使う。`@RunInOrder` は並列化を妨げ再テストも頭からになるので、まず1つの `@Test` にまとめられないかを考える
- 見直す条件: 属性の付いたクラスの寄せ方で run 全体が目に見えて延びる実例が出たとき。OS が混ざったクラスを順に流す必要がある実例が出たとき

## DR-208 メモはテスト1本の中だけにし、run 全体で共有する値は `writeRunMemo` 等の別の関数でマシンをまたいで1つにする(DR-142・DR-207 の範囲を置き換える。排他は DR-210 で見直した)

  持ち主が落ちたときの回収の規則まで要るため(DB なら既に排他を持つ)

## DR-209 run 全体の準備と片付けは `beforeRun()` / `afterRun()` で、発行元のマシンで1回だけ走らせる

- 種別: 方針
- 決定: ユーザー 2026-11-20
- 内容: `@RunHooks` を付けたクラス(プロジェクトに1つだけ)に `beforeRun()` / `afterRun()` を書く。どちらも**スケジューリングを行うマシン(発行元)で
  run に1回だけ**走る(1台のマシンだけの run ならそのマシン)。`beforeRun()` はどのマシンのどのシナリオよりも前、`afterRun()` は全マシンの仕事が
  終わった後。**デバイスを操作するコマンドは使えない**(発行元にデバイスがあるとは限らない)。使えるのはデバイスの要らないもの(run メモ・
  `httpRequest`・`data()` / `account()` 等)。`beforeRun()` の失敗は run を止める(シナリオを1本も流さない)。`afterRun()` は失敗した run の後でも
  走り(`beforeRun()` が失敗しても走る = 途中まで作った分を片付けられる)、合否には数えない(中断した run では走らない)。
  `beforeRun()` で書いた run メモは全シナリオの開始より前に確定する。**`beforeRun()` から届くのは全マシンが共有する外部のサーバーだけ**で、
  compose.yaml のマシンごとのコンテナの準備は `run-setup.sh` / `beforeAll()` に置く。宛先の許可・データセットの上書きも走ったマシンの設定で動く
  (1台のリモートへ丸ごと配る run ではランナー機)。
  範囲は**1回の run × 1つのプロジェクト**(同じプロジェクトを複数のプロファイルで回す run でも1回)。`beforeRun()` の失敗は中断と混ぜない専用の終わり方。
  `afterRun()` は `afterAll()` と同じく「走れたら走る」: 全マシンの子が正常に終わったときだけ走らせ、中断・異常終了では走らせずに1行出す(取りこぼしを後で回収する
  仕組みは作らない = 2026-11-20 の敵対的レビュー4回で、回収と終わりの確認が毎回新しい穴を生んだため)。`@RunHooks` があるプロジェクトの `--fleet` は断る。
  親とつながった子は、発行元から開始の行を受けるまでシナリオを流し始めない(`beforeRun` の失敗は取りやめの行で畳む)。
  同じプロジェクトの別の run と時間が重なったら開始時に1行出す。ロック(DR-210)とは段を分けて先に作る。
  `@RunHooks` のクラスが2つ以上あれば run の開始前にエラー。細部は RR-8.4
- 理由: `run-setup.sh` / `beforeAll()` はマシンごとに走り、run 全体で1回だけ走る口が無かった(DR-205 の見直す条件)。全体で1回にすると、
  run メモに書く準備を「何度走っても壊れない形」にしなくてよい。置き場をプロジェクトに1か所にするのは他のツールの慣例
  (TestNG の `@BeforeSuite`・Jest / Playwright の `globalSetup`・pytest の session スコープ)。デバイスを使えなくするのは、発行元にデバイスが
  無い構成(配るだけのマシン)でも同じシナリオが動くようにするため(デバイスの準備は `beforeAll()` / `setUpDevice()` が受け持つ)
- 見直す条件: run 全体の準備でデバイスを使う必要がある実例が出たとき
- 参照元: docs/remote-runner/01-11.md(RR-8.4)

## DR-210 run 全体で効く排他ロックを `withRunLock` のブロックで置き、入れ子を禁じてデッドロックを作れなくする(DR-208 の「排他は持たない」を見直す)

- 種別: 方針
- 決定: ユーザー 2026-11-20(共有ロックの撤去と入れ子の全面禁止は同日のユーザー決定で改訂。名前は 2026-11-21 のユーザー決定で `withRunLock` —— 共有ロックが無いので「排他」は区別の役を持たず、`writeRunMemo` 等と同じく範囲(run 全体)を名前に出す)
- 内容: `withRunLock("キー", …) { }`(ブロックの形だけ。取る・外すを別々に呼ぶ形は置かない)。**共有ロックは置かない**。
  **第2段**(`beforeRun` / `afterRun` の後)。設計の敵対的レビューを5回回した後に実装し、以後はコードでレビューする(ユーザー決定 2026-11-20)。
  **通り道はロック専用の接続**(ユーザー決定 2026-11-20): 発行元がロックのサーバーを unix ソケットで起こし、各シナリオのプロセスが自分のマシンのソケットへ直接つなぐ
  (リモートは中継役が今の ssh に unix ソケットの転送を足す)。親子の間の `ftWork` の行には載せない(stdout と stderr の混ざり・PIPE_BUF を超える行の混ざり・
  端末のエコーで行が黙って欠けうる。行に載せた設計は敵対的レビューで4回続けて重大が出た = 欠けのたびに永久の待ち・幽霊の持ち主・書き込みの消失)。
  **ロックの中の** run メモの書き込みだけをその接続で送り、確定の返事を待つ(「外す」より前に確定する。同じ接続の順序で保証)。ロックの外の書き込みは今の通り道のまま(全部を接続へ移すと DR-208 の同じマシンでの見え方の保証が後退する)。
  ロックの中の `readRunMemo` は接続で最新の値を聞く。範囲は**1回の run × 1つのプロジェクト**で、1台のマシンだけの run でも同じ関数がそのまま効く
  (MCP の `ft_run_scenario` は MCP サーバーが発行元)。`--fleet` と、ソケットを渡されなかった親とつながった子では、ロックを呼んだ時点で失敗にする
  (黙ってマシンごとに割れると誤った緑)。取れるまで待ち、**待った時間は `scenarioTimeout` の締め切りから外す**(台数を増やすほど時々赤になる形を作らない)。
  **1回の呼び出しの待ちの絶対の上限はその run の最も長い `scenarioTimeout`**(`@Test(scenarioTimeout:)` を含む。激しい取り合いで台数を増やすと当たりうることは
  docs に書いて許容する)。`waitSeconds:` を渡すとその値。上限はシナリオのプロセスが自分の時計で判定する。
  **接続が「外す」無しに閉じたら**、手元の待ち受けの接続は相手の pid の終わり(`NOTE_EXIT`)を待ってから外し(pid が分からなければ持ったまま)、リモートの待ち受けの接続(ssh の転送)は「持ち主不明」にする。先に `scenarioEnded` を受けていれば、閉じたことは外したと扱う。持ち主不明のキーへの要求は、
  待たせずにすぐ失敗させる。中継役が向こうの run の終わりを確かめたら外し
  (その run の最も長い `scenarioTimeout` に後始末の猶予を足した上限まで確かめ直す)、以後そのキーを取ったステップには前の持ち主の書き込みが欠けているかも
  しれない旨を注記する。run の終わりはロックの状態に依存させない。失敗の後はロックの本体を実行せず、外すのはブロックを抜けた時点。
  デッドロックは次の規則で作れなくする: ①1回の呼び出しに複数のキーを渡すと名前の順(UTF-8 のバイト列の比較)に1つずつ取り、取った分は持ったまま次を待つ
  (1回の呼び出しの中の同じキーは重複を除く) ②**ロックの中でロックを呼ぶとエラー**(別のキーでも同じキーでも。競合の有無に関わらず取ろうとした時点で。
  要るキーは全部1回の呼び出しで渡す)。入れ子が無く、全員が同じ順でしか待たないので待ちの輪はできない。
  **キーの長さと個数に上限を置かない**(ユーザー決定 2026-11-21。当初の 120 バイト・8 個の根拠「端末を通る行は約 1024 バイトで切れる」は、キーが端末の入力側を通らないので当たらない = DR-4)。
  細部は RR-8.5
- 理由: 最初に1台のマシンで run メモを使っていたテストを複数マシンの並列へ広げるとき、排他が無いと DB へ書き換えが要り、
  複数マシンへ広げるのをためらわせる(fleetest の利点が半減する)。DB を使う案内は残す。用途は「1つしかない資源(OTP の受信箱・同時に1台しかログインできないアカウント等)を、デバイスの操作をまたいで占有する」
  (DB はデータの排他しか持てない)。共有ロックを置かないのは、読み手と書き手を分ける実例が無く、共有の中での書き込みの禁止・排他への格上げ・
  持ち主不明の共有の扱いと覚えることだけが増えるため。入れ子を全面に禁じるのは、名前の順の規則と再入の数えを利用者に覚えさせずに済み、
  エラーがタイミングに依らず決まるため(ヘルパー関数の中でロックを取る書き方はできなくなる)。入れ子を自由にしてデッドロックを検出する形は採らない
  (赤になるかが他のテストとのタイミングしだいになり、1台では緑・複数台でだけ時々赤、という形を作るため)。1回の呼び出しの中の順番を名前の比較にしたのは、
  宣言の口を足さずに全員が同じ順番を共有できるため。通り道を専用の接続にしたのは、行の通り道の欠けを番号の検出・上限・注記で塞ぐたびに
  別の穴が出て収束しなかったため(接続1本ごとに順序と区切りが保証され、シナリオのプロセスが死ねば接続が閉じる)
- 見直す条件: 入れ子が要る実例(1回の呼び出しにキーをまとめられない書き方)が出たとき。読むだけのシナリオどうしを同時に走らせないと遅すぎる実例が出たとき(共有ロック)
- 参照元: docs/remote-runner/01-11.md(RR-8.5)・docs/user-docs/reference/commands/memo(_ja).md

## DR-223 表示条件の組み合わせは実行プロファイルの `variants`(名前付きの一覧)で回し、実行の単位をシナリオ × バリアントにする

- 種別: 方針
- 決定: ユーザー 2026-11-22
- 内容: 実行プロファイルの `variants: [{name, appearance?, textSize?, orientation?}]` が組み合わせの宣言で、総当たりの書き方は置かない。
  名前は必須・一意・`[a-z][a-z0-9-]*`。知らないキー・重複・空の一覧・不正な値は実行前にエラー。書かないキーはプロファイルの最上位の同じキー、
  それも無ければ基準の値(light / default)に解決し、**解決した値は「指定あり」として扱う**(合わせられなければそのシナリオを失敗にする = DR-221。
  `default` という名前のバリアントが合わせられないまま緑で残るのを防ぐ)。どれかのバリアントが `orientation` を書くなら全バリアントが書く
  (または最上位に `orientation` を置く)ことを求める。各シナリオが子の起動直後に自分の向きへ回すので、前のシナリオの向きが残っても必ず上書きされ、
  親が向きを戻す仕組みは置かない。`variants` のあるプロファイルでは `--set appearance=` / `textSize=` / `orientation=` / `variants=` を実行前にエラーにする。
  バリアントの値は OS に依らない語彙で、iOS と Android が混在するプロファイルでも同じ意味で効く(OS ごとの節を持たない)
- 理由: 組み合わせを名前付きの一覧にすると、結果・`--failed`・LPT・集計の鍵(シナリオ ID × バリアント名)が人に読める形で決まる。総当たりは
  本数が掛け算で増え、意図しない組み合わせまで回す。解決した値を指定ありにしないと、基準と同じ値のバリアントだけ「合わせられなくても警告で続く」扱いになり、
  同じ名前の run が端末によって違う条件で緑になる。`--set` で値だけ変えると名前と中身がずれ、結果の鍵が嘘になる(値を変えたいならバリアントを足す)

- 決定: ユーザー 2026-11-26(「11/10 の決定を変えてよい」)
- 内容: tap が木の枠の中心を撃つ経路で、塗り順の分からない木(`PaintOrder.isReal` が偽 = Flutter・CMP・SwiftUI 等)のときだけ、対象の中心にラベル(無ければ値)を持つ別の要素が重なっていれば(祖先・子孫を除く)、撃つ前に対象の枠を OCR で1回読む。自分の文字が読めず、重なる要素の文字が読めたら注記 `tap-target-drawn-over`(座標で撃った回 = その要素に当たったかもしれない / in-app の activate で押した回 = 画面では覆われていて人には押せない)。**新しい検知なので警告から**(合否は変えない)。重なりの無い tap は読まない(費用は重なりがある回だけ = 11/10 に不採用とした「全 tap の費用」にならない)。OCR の段が無効・自分の文字が無い要素は読まない

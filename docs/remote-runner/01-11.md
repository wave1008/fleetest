| 種別 | 範囲 | 読む場面 | 扱わないこと |

リモート実行の基本設計。用語の定義(RR-0)は [spec.md](spec.md)。

## RR-1 前提と目的

- **マシンは Mac に統一**(DR-99。クライアント・実行側とも)。
  非 Mac クライアントからの実行という要件は存在しない
- CI は self-hosted Jenkins / EC2 Mac([ci.md](../ci.md))。**ジョブ粒度のリモート実行は
  CI が既に担っている**ため、本構想の固有価値は CI を経由しない対話的用途に限られる:
  1. **Mac フリートへのシナリオ並列分散**(夜間回帰のスループット。FM はホスト単位で
     許可枠に制限される共有資源(PT-3.5)のため、1台に集約すると枠で
     頭打ちになる。台数分に分散すれば機械ごとに別の枠が使え、screenLooksLike 多用スイートは
     台数分の実質短縮になる)
  2. **デバイス/実機ラボの共有**(iOS 実機は元々 LAN/iproxy の2択で相性は悪くない)

## RR-2 却下済みの代替案(再提案しない)

| 案 | 内容 | 却下理由 |
|---|---|---|
| A. ブリッジ層で切る | `BridgeClient` の HTTP を遠隔ホストへ向ける | ステップ毎 snapshot の chatty なプロトコルに LAN RTT が乗り、ms 級チューニング(stale-guard 350ms・LPT 等)が崩れる。プロビジョニング(ブート・ランナービルド・インストール・ゾンビ掃除・凍結復旧)は全部ローカルプロセス制御前提で、遠隔化には常駐エージェント=第二プロダクトが要る |
| B. 独自プロトコルの常駐デーモン | fleetestd を立ててクライアントが接続 | 全マシン Mac なのでどのマシンもフルスタックが動き、役割分離の動機が無い。ジョブ粒度なら Jenkins の再発明。認証/TLS の自前実装が必要 |
| FM 分離構成 | デバイスは VM ファーム・FM は手元物理 Mac(案A の副産物) | 全 Mac(物理)前提で動機消滅 |

## RR-3 採用方針: ジョブ(run)単位の SSH ディスパッチ

**対等ピアモデル**。どの Mac も clone + `Scripts/install.sh` で同一状態になれるので、
リモート実行=「向こうの Mac で普通にローカル実行し、結果を手元へストリームする」だけにする。
新プロトコル・認証・常駐デーモンは作らない(トランスポートは SSH)。

`fleetest run --runner <mac>` の流れ(アプリは転送しない。ランナー側の配置は RR-14・RR-18.6):

1. 適合チェック(RR-7。不一致は fail fast)
2. 転送(rsync: シナリオ・プロファイル)。**リモートは外部構成(WORK_DIR 分離)前提・
   rsync 先はリモートの WORK_DIR**(実装は RR-18.6 の `<base>/users/<issuer>/work`)。
   **相手のローカルインストールと同じ場所に置かない** — `--delete` が相手の資産を消し、
   クローン共用は SPM ビルドロック競合を起こす(実害3件は [records.md](records.md) の RR-12)
3. リモートで実行(`install.sh` は `remote setup` が済ませる。RR-14)。転送後はリモートで scenario ターゲットの
   swift build が走る(コールドは数分。`clean -fd` に `-x` を付けない= .build 温存の
   既存設計が増分ビルドを効かせる)
4. **ストリームバックの実体は用途で分ける**: CLI/CI は `fleetest run --quiet --junit` の
   出力中継、拡張(レーン表示)連携は `fleetest api run` の NDJSON 中継
   (`fleetest run` は人間向け出力で NDJSON を喋らない。ApiRunCommand が唯一の機械可読契約)
5. 成果物回収(reports/・JUnit・results DB・録画)。**JUnit 内 `report:` 行は
   リモートの絶対パス**なので回収後のローカルパスへ書き換える。
   回収物は**リモートが生成した外部入力**として扱う(RR-15)

**禁止事項(実装者向け・摩擦が出ても回避しない)**:

- **`StrictHostKeyChecking` を無効化しない**(`-o StrictHostKeyChecking=no` を足さない)。
  ホスト鍵検証は MITM に対する唯一の防御であり、同時に「設定の乗っ取りで未知ホストへ
  ディスパッチされる」経路を実際に塞いでいる(RR-15)。初回接続の TOFU は
  `ssh-copy-id` の手動ステップ(RR-14 ステップ0)で人間が1回だけ行う
- **`--remote-dir` を実行ごとの自由入力にしない**。転送は `--delete` 付きでリモートの
  ディレクトリを上書きするため、宛先は**登録簿(RR-13)に登録された値のみ**を使う

**ホスト混在プロファイル(devices に `host: "local"` と `host: "M1Max"` 等が並ぶ形)を
`--runner <名前>` で単一ホストへ送るときは、そのホスト担当のデバイスだけが
`--device`/`--device-machine` として自動で付く**(丸ごと送ると受け側の「local」枠が発行元の
Mac のデバイスに解決され、存在しないデバイスの起動を試みるため)。担当が1台も無いプロファイルは
ディスパッチ前にエラーで止まる。

## RR-4 全体アーキテクチャ

```
┌─ ローカル Mac(発行側)────────────────────────────┐
│ fleetest run --runner mac2 --profile …              │
│  ├─ 適合チェック(rev / Toolchain)                │
│  ├─ dispatch.lock の取得(待機列。RR-13・RR-18)   │
│  ├─ 転送(rsync: シナリオ・プロファイル)          │
│  ├─ NDJSON 受信 → 進捗表示・拡張へ中継            │
│  └─ 成果物回収(reports/ ・junit.xml・録画・run ログ)│
└───────────────┬────────────────────────────────────┘
                │ SSH
┌───────────────▼─ リモート Mac(実行側)────────────┐
│ sshd のプロセスが fleetest run --runner local を   │
│ 直接実行(Aqua セッションが存在することが前提。RR-5) │
│  └─ シミュレータ・XCUITest・FM・エミュレータ        │
└────────────────────────────────────────────────────┘
```

## RR-5 Aqua セッションの前提と実行の置き場(GUI セッション制約への回答)

GUI 依存は fleetest のコードではなく **macOS のセッション意味論**に由来する
(launchd のセッション種別が Background[SSH 直・LaunchDaemon]か Aqua かで
WindowServer・ユーザー空間サービスへのアクセスが変わる。
「ログインなしで Aqua を作る」公式手段は macOS に無い)。よってコード分離では消せず、
**Aqua セッションが存在すること**を前提に置く。

| コンポーネント | Aqua セッション | 備考 |
|---|---|---|
| iOS シミュレータ + XCUITest | 存在が必須 | レンダリング・スクリーンショット・XCUITest はユーザーの launchd ドメインのサービスに依存する。本ツールはスナップショット・録画多用で回避不能 |
| FM(FTFoundationModels) | 存在が必須 | Apple Intelligence のデーモン群はユーザーセッション側 |
| Android エミュレータ | 存在が前提 | `-no-window` で起動し、SSH セッションから動く(RR-6) |
| コンパイル・オーケストレーション・results・align | 不要 | 純粋にプロセスとファイル |

- **常駐エージェントは持たない**。発行側が rsync で転送したあと、ssh でランナー機の
  `fleetest run --runner local` を直接実行する(`--runner local` はランナー側での再ディスパッチを止める)。
  判断・プロビジョニングは fleetest 本体にあり、ランナー側に加える機構は無い
  (.claude/rules/installer-agents.md「機械作業はスクリプト/CLI に寄せ、スキルには判断だけ残す」と同じ方針)
- **1マシン1 run は `dispatch.lock`(RR-13)で守る**。同一リモートへの同時ディスパッチはデバイス割当と
  loopback のポートが競合するため、FIFO の待機列(RR-18)に並べて1本ずつ通す。**その機械で直接打った run
  (`fleetest run` / `fleetest api run`・fan-out の local エントリ)も同じロックを取る**
  (`Sources/fleetest/LocalDispatchLock.swift`)ので、他人のディスパッチと手元の run も重ならない
### 運用前提(Aqua セッションの寿命と2モード)

**自動ログインを無条件必須にはしない**(モード B 限定の選択肢。下記)。macOS は
FileVault 有効時に自動ログインを無効化するため、「自動ログイン必須」はランナー機の
FileVault を捨てることと同義になる。ランナーには SSH 鍵・ソース・シナリオ(テスト資格情報を
含み得る)・録画が載るので、既定は FileVault 有効(モード A)とし、
**Aqua セッションの寿命**に着目して要件を組み直す:

| 事象 | Aqua セッションへの影響 | 対処 |
|---|---|---|
| 画面ロック | **消えない**(セッションは生きたまま) | ロックは**有効のままでよい**(RR-9 で XCUITest/録画の可否を実測) |
| ディスプレイスリープ | 消えない | 可 |
| **システムスリープ** | 実質停止 | `pmset` で**無効必須**(`sudo pmset -a sleep 0`) |
| **再起動・電源断** | **消える**(loginwindow で停止) | 人が1回ログインして復帰(下記) |

つまり**セッションを失うのは再起動だけ**で、それ以外は無人で回り続ける。再起動は OS 更新
程度の頻度なので、「再起動のたびに人が1回だけ解錠・ログインする」運用は成立する:

- **計画再起動**: `sudo fdesetup authrestart` で再起動すると、次回起動時の
  FileVault 事前認証をスキップしてボリュームが解錠される(遠隔管理用の標準機構)。
  ただし**解錠 ≠ ログイン**なので、その後に画面共有(またはコンソール)で1回ログインして
  Aqua セッションを立てる。
  **実行は人が対話 ssh(または画面共有)で行う手作業** — ディスパッチ経路は
  `BatchMode=yes` で sudo プロンプトに応答できず、NOPASSWD 設定は攻撃面を広げるので
  作らない(再起動は稀なので手作業に倒す。2026-07-31 決定)
- **不意の電源断**: 事前認証から人手で解錠+ログイン。**画面共有(Screen Sharing)を
  有効にしておく**と手元から実施できる(ステップ0 の必須項目)
- **「ログインしていない」を機械で検出する**: `stat -f%Su /dev/console` がランナー
  ユーザーと一致するかを preflight とディスパッチ前チェックに入れ、不一致なら
  **「ランナーが loginwindow で待機中 — 解錠が必要」と明示して落とす**。入れないと
  シミュレータ側の不可解な失敗として現れて切り分けに時間を溶かす

### サポートする2モード(どちらも正式構成)

再起動後の復帰手段だけが違う。**どちらを採るかはランナー機の設置環境で決める**。

| | モード A: FileVault 有効(既定) | モード B: FileVault 無効 + 自動ログイン |
|---|---|---|
| 再起動後 | 人が1回**解錠+ログイン**(画面共有可) | **ゼロタッチ**で Aqua が立つ |
| 平常時 | 無人 | 無人 |
| 向く設置 | 共用オフィス・持ち出し得る機械 | 施錠されたラボ・EC2 Mac 等の専用機 |
| 受容するリスク | — | 起動できる人がデータに到達。自動ログインは `/etc/kcpassword` にログインパスワードを可逆保存(RR-15.4) |
| 設定 | `fdesetup` 有効・自動ログインなし | `fdesetup` 無効・`autoLoginUser` 設定 |

- **Apple silicon ではモード B でもディスクは常時暗号化されている**(ハードウェア鍵)。
  FileVault の有無は「起動時に鍵が自動で使えるか/資格情報を要求するか」の差であり、
  「平文で置かれる」わけではない。ただし**その機械を起動できる人はデータに到達できる**
- 画面ロックの扱いは**両モード共通**(ロックはセッションを消さないので有効のままでよい。
  実測は [records.md](records.md) の RR-9 実験②が未実施)。システムスリープ無効も共通
- **準備状態の判定は両モード共通で `stat -f%Su /dev/console`**(Aqua セッションが
  立っているか)。モードが変えるのは**失われたときの復帰手段だけ**なので、ディスパッチ側の
  チェックはモードを知る必要がない。モード判定(`fdesetup status` + `autoLoginUser`)は
  **preflight が「復帰手順の案内文」を出し分けるためだけに使う**
  (モード A: 「解錠+ログインが必要」/ モード B: 「自動ログインが効いていない — 設定を確認」)
- **到達経路は「SSH の Background セッションでそのまま実行する」1つだけ**(2026-07-31 実測)。
  コンソールに誰かがログインしていれば、SSH 側のプロセスからでもユーザーの launchd ドメインの
  サービス(CoreSimulator 等)に到達でき、シミュレータ・XCUITest・in-app ブリッジまで動く。
  したがって上表の「Aqua 必須?」は正確には**「Aqua セッションが存在すること」が必須**で、
  実行プロセスがその中にいる必要はない
- **`launchctl asuser` 経由の注入は使わない(DR-100)**。`asuser` は **root を
  要求**し(`Could not switch to audit session`)、sudo を作らない方針では使えないため。
  セッションモードの選択肢自体を持たない(`--remote-session` は無い)。**再提案しない**

## RR-6 Android の SSH 実行

**エミュレータは `-no-window` で起動している**(`DeviceBooter.startEmulator` が
`-no-snapshot -no-window -no-boot-anim -no-audio -gpu host` を渡す。プロセスの実体も
`qemu-system-aarch64-headless`)。したがって既知の凍結知見(複数台同時描画がトリガ・
sleep/wake で修復)は**すべてヘッドレス環境で得られたもの**で、「窓あり前提」ではない。
`-no-window` 採用の条件だった2項目は検証済み。

実測(SSH の Background セッションから):

| 項目 | 結果 |
|---|---|
| エミュレータの起動 | ✅ 16秒で起動(`-no-window -gpu host`。**Metal も SSH セッションから使える**) |
| Android シナリオの実行 | ✅ 完走(ディスパッチ経由・exit 0) |
| gRPC 制御(`EmulatorControl.shutdown`) | ✅ 動作(2秒で停止。gRPC ポートは `[::1]` に listen し、同一マシンの SSH セッションから到達できる) |

**残る本当の論点は「Aqua セッションが無い(loginwindow のまま)状態で動くか」**で、これは
RR-5 のログイン検出(RR-16.3)が塞いでいる領域。iOS と同様、**Android も「Aqua セッションが
存在すること」を前提にする**(未ログイン状態での検証は未実施)。よって
「Android だけログイン不要のレーンに振り分ける」最適化は**現時点では成立が確認できていない**。

**ディスパッチ前にエミュレータを起こす必要は無い**: プロファイル実行(`ProfileSupplyLanes`)が
未起動の AVD を起こす(`AndroidLaneRecovery.bootMissingDevices`)

## RR-7 版整合・更新

- リモート側も clone + ソースビルド(配布方針どおり)。更新は `fleetest remote align <runner>`
  (全機は `Scripts/align.sh`)
- ディスパッチ前の適合チェックは**2項目**: **git revision・ToolchainFingerprint
  (Xcode の版 + iOS Simulator SDK のビルド。**macOS の版は含まない**)**。
  **machineName は照合しない** —— 「送り先が想定の機械か」は ssh の宛先(とホスト鍵)が
  保証するので、リモートの登録名は見ない(`RemoteCompat.verdict`)。
  git revision の不一致は**黙って走らせず fail fast**(このリポジトリの
  「片方だけ変えない」規律をマシン間に広げると、スキューは恒常的なバグ族になるため
  入口で遮断する)。**ToolchainFingerprint だけは仕分けが1段深い**(DR-101): 製品版
  (`Xcode X.Y`)が同じで build 番号だけ違う = ベータの seed 違いはディスパッチを**止めない
  advisory**、製品版が違う(26 vs 27 等)は従来どおり fail-closed。根拠は、リモートへ渡るのが
  TestProjects のソースだけで、fleetest 本体・XCUITest ランナー・in-app dylib は**ランナー機が
  自分の Xcode でビルドする**ため機械的な依存が無く、止める理由が「結果の比較可能性」だけに
  縮むこと(実質的な結合は `appPath` のアプリが手元ビルドのままワークスペース経由でランナーへ
  入る1点だけ)。仕分けは `fleetest api remote-compat` / `fleetest remote status --json` の
  `toolchainAdvisory: String?` が持ち、`toolchainCompatible` は「blocking で止まるか」の意味になる
  (advisory のときも true)
- **ランナーに複数の Xcode が入っているときは、発行側の Xcode に一致するものへディスパッチが
  自動で選ぶ**(DR-102)。選ぶのは **`DEVELOPER_DIR`**(プロセス単位・sudo 不要)——
  **`xcode-select -s` は使わない**: 機械全体に効き sudo が要るので、共有ランナーでは自分の選択が
  他の利用者の run を壊す。候補はランナーの **`/Applications` 直下**の `Xcode*.app` だけ
  (`CFBundleShortVersionString` / `ProductBuildVersion` を読む)。**別の場所に置いた Xcode は
  見つからないので登録簿の pin(`RemoteHostEntry.developerDir`)で指定する**。選択規則
  (この順): ①pin があればそれ ②build 番号まで一致する候補がちょうど1つならそれ ③製品版
  (`Xcode X.Y`)が一致する候補がちょうど1つならそれ ④候補が空(列挙できない・Xcode が無い)なら
  何もしない(従来どおり ambient = `xcode-select -p` の結果)⑤一致0個・複数なら**候補一覧を出して
  ディスパッチを拒否**する(手近な Xcode へ黙って倒さない)。**適合チェック(probe)と実行(run)は
  必ず同じ `DEVELOPER_DIR` の解決を通る** —— 食い違うと「照合した Xcode と違う Xcode で走る」
  沈黙した退行になる。**`remote align`(`Scripts/align.sh`)のビルドも同じ解決を通す**
  (`alignRevisionCommand(developerDir:)`。一致しない・列挙できないときは ambient で、一致しないときは1行警告する)
  —— 通さないとランナーの `xcode-select -p` の結果でビルドし、それがコマンドラインツールだと FoundationModels の
  マクロが無くてビルドが落ちる(M1mini で実測)。**モニター(デバイスの状態・ライブ映像)には効かせない** —— 観測は
  dispatch.lock の外で常時走るので、版の違う simctl を同じ CoreSimulatorService に当てる危険を
  増やさない。効果として、**Xcode の製品版が違うランナーも、その製品版の Xcode さえ入っていれば
  フリートに混ぜられる**(この選択が無ければ製品版違い = 常にディスパッチが止まる)。
  **iOS シミュレータのランタイムは Xcode に付いてこない**(CoreSimulator のランタイムは機械共有)
  ので、選んだ Xcode の製品版に対応するランタイムが無ければ起動できない —— `remote status` の
  RUNTIME 欄が既にこれを警告する。**製品版をまたいでフリートを混ぜると、OCR・FM は OS 付属**
  なので結果が機械で変わりうる(既存の macOS 混在の注意と同じ)。赤の帰属は run.json の
  `toolchain` 欄(docs/results-json.md)で追える
- **照会そのものが失敗したときは理由まで出す**(2026-09-09)。`RemoteCompat.ProbeOutcome` が
  「値が無い」と「なぜ取れなかったか」を別に持ち、ssh の exit status とリモートの出力を
  reasons へ載せる。**照会系は1回だけ引き直す**(待ち時間は置かない) —— ssh の単発失敗は
  そのレーンのシナリオを丸ごと捨てるのに対し、引き直しは ssh 1往復で済む。
  **判定は緩めない**: 2回とも失敗すれば fail-closed のまま非互換で落ちる
- **rev 一致の意味 = ツールの中身の要約が一致すること**(コミットの SHA ではない)。要約は手元の作業ツリー
  (未コミット・未追跡を含む。.gitignore は効く)から作り、`TestProjects/` は除く(run のたびに rsync で届くため)。
  手元にツール本体の未コミットの変更があれば、align し直すまでディスパッチが止まる。
  **要約は2種類**(DR-226): align の送る・ビルドの記録・送った後の検証は**全体の要約**、参加を断るかの照合(ディスパッチ・`remote status` の適合・`api remote-compat`)は
  全体から更に直下の `docs`・直下の `.md`・`.claude` を除いた**判定用の要約**(`AlignSnapshot.runDigest`)で比べる(docs だけの違いでは断らない)。
  ランナーの照会は5行(HEAD / 全体の要約 / 判定用の要約 / 基点 / 発行者)。
  未コミット・未 push でも align で揃えられる(次の項)
- **照合するのは「rev に包含されないもの」だけ**という原則で照合項目が決まる —
  Toolchain(マシンごとの Xcode/SDK)と machineName(リポジトリ管理外のローカル設定)は
  rev では担保されない。**`ProtocolVersion` は照合しない**(リポジトリ管理下なので
  rev 一致に包含される。RR-12 の結論)
- リモートの **TOOL_ROOT 解決は既存4箇所の規則を再利用**する(preflight.sh / update.sh /
  toolRootResolve.ts / Package.swift 宣言。`toolRootContract.test.mjs` の対象)。
  ディスパッチ用の独自解決を新設しない
- **実行前に版ズレだけを問い合わせる口は `fleetest api remote-compat --project <P> --profile <X>`**
  (JSON。人が読む表は `fleetest remote status`)。拡張はこれで実行プロファイルのリモートホスト
  全部の rev/toolchain 適合を見て、ズレていれば「更新して実行 / キャンセル」をダイアログで聞く
  (**「そのまま実行」は置かない** —— ズレたまま走らせるとリモート担当分は必ず
  checkCompatibility に弾かれ、部分失敗の run にしかならない。align で直せないズレ
  = 到達不能・製品版の違う toolchain 不一致・この機械が古い/分岐は実行を止めて理由を出す(ベータ seed 違いの
  toolchain advisory は止めない)。チェック自体を外すのは
  設定 `fleetest.remoteCompatCheck`)。ズレの解消(揃えるだけ)は `fleetest remote align <runner>` —
  `remote setup` の align ステップだけを単独で実行する軽量版(preflight/install は通さない)

  **`remote align` は push が要らない直送**: 手元の作業ツリーを1つのコミット(きれいなら HEAD そのもの・汚れていれば
  親 = HEAD の目印付きスナップショット)にして、ランナーのクローンへ ssh で直接 `git push` し、checkout してビルドする。
  origin への push は要らない。中身の要約が既に同じなら何もせずに即座に終わる。ビルドは
  **全製品(`fleetest`・`fleetest-services`・配信ヘルパー3本・`fleetest-mcp`)を dispatch.lock の下で行い**、`fleetest` 以外は
  依存のソースが前回の成功したビルドから変わっていなければ省く(`RemoteAlignPlan.productSourceClosure`。`swift build` も重い負荷で、
  ロックの外へ出すと直後の run と CPU を取り合い SwiftPM が `.build/debug` のリンクを作り直す瞬間に run の exec が落ちる)。
  成功したビルドの記録(`.fleetest/align-built`)が HEAD の要約と食い違うクローン(align のビルドが終わっていない・align の外で中身が変わった。どちらかはツールには分けられない)は照会が `built: false` と読み、
  要約が手元と同じでも照合は止まる(`unbuilt:`)。他の発行者が置いたスナップショットがランナーにあっても止めずに上書きし、照合の案内でその発行者を名指しする(RR-18.3)

  **`run --align` / `api run --align`** はディスパッチの直前にこの揃えを同じ関数(`RemoteAlign.execute`)で行う(要約が一致なら何もしない・`remoteBehind` / `workingTreeDiffers` は揃える・`localBehind` / `diverged` / `unknown` はランナーを巻き戻さず `relationAdvice` の文で止める = RR-18.3 規則1。**ランナーの照会そのものが読めない(ssh の失敗・行数不足)ときも止める**。純粋部分は `RemoteAlignPlan.alignDecision`)。**`--tool-rev` を明示したときはこの安全弁を掛けない**(人が版を名指ししている = `remote align --tool-rev` と同じ。「直す前の版」へ揃える機能)。**`--tool-rev <rev>`** は手元の値(要約・向きの基点)を作業ツリーでなく `<rev>` のコミットのツリーから求める(`RemoteCompat.localTool` の1箇所。`remote align --tool-rev` はそのコミットそのものを送る)。2台へ別の版を同時に回すための口で、どちらも**単一のリモートへのディスパッチだけ**(手元・`--fleet`・`--target`・機械分担は撃つ前に断る。子へは渡さない)

  **手元を更新したあと全機を揃えるときは `Scripts/align.sh [<machine>...]`**(省略時は登録簿の有効な全機へ
  `remote align` を**並列で**投げる → `remote status --json` の各機の `revisionCompatible` が全部 true になるまで確かめる)。
  `remote align` は1機ずつしか受け取らないので、素で使うと**人の手では必ず直列になる**
  (前の機の出力を読んでから次を送る形になる)。台数ぶん待ちが伸びるだけの誤りなので、判断の余地を機械へ移してある。
  コミットも push もしない(直送するので不要)

## RR-8 マルチマシン分散(`run --fleet --split`)

- `RunOrchestrator` の worker 抽象はマシン跨ぎへ拡張しない。
  分散は**ディスパッチの手前**(発行側)で行う: シナリオ一覧をローカルで解決 → LPT で
  エントリへ割り当て → 確定した `--scenario` を各エントリへ渡す。各ホストの中では
  従来どおり `RunOrchestrator` が自分のデバイスへ割り当てるので、**2階層が独立**に働く
  (マシン跨ぎの worker 抽象を作ると、ホスト内のデバイス割当と二重管理になる)
- 見積りは既存の `LPTScheduler`(results の中央値)を再利用する。**新しい実績の仕組みを作らない**
- **platform 適合を守る**(iOS 専用シナリオは iOS を走らせられるエントリへ)。どこにも
  入らないシナリオがあれば**throw して止める** —— 黙って落とすと「走ったつもりで
  走っていない」を作る。エントリの platform は実行プロファイルの devices が直接持つ
  (実行プロファイルはプロジェクト資産なので ssh 無しで解決できる)
- **割り当ては決定的**(同着はシナリオ ID、負荷同着はエントリ順)。前回と同じ割り当てを
  再現できないと flake の切り分けにならない
- **実績が1件も無いとき**は全シナリオが同じ重みになり、LPT は本数の均等割りに退化する。
  このとき重みの絶対値は割り当てに影響しないので、**根拠のある秒数を選ぶ問題自体が無い**
  (テストで「値を変えても同じ割り当て」を固定)。秒と誤読されないよう推定列は出さない
- `--split` のときだけローカルビルドが要る(一覧の解決)。プレーンな `--fleet` の経路は変えない

**実測(2026-08-16。E2E-iOS 23本 / M1Ultra + M1Max)**: 11 + 12 本に分かれ、
推定 133.4s / 135.7s に対し実測のテスト時間 130.5s / 128.9s(**誤差 2〜5%**)。
壁時計は 2分56秒(1台で23本走らせるとテスト時間だけで約 259s)。
- results DB のマージは不要(集計は results/ を走査するファイルベースで、回収した時点で載る。
  RR-13 末尾)。レポート内パスの書き換えは `RemoteReportLink`(記録側)/
  `RemotePathRewrite`(JUnit・NDJSON)。
  **JUnit の集約**: `run --fleet --junit <path>` が1ファイルにまとめる。
  各エントリには一時パスの `--junit` を渡し、完了後に `FTCore.JUnitMerge` で結合する)。
  **読めないエントリを黙って省かない**のが要点 —— 出力が無い/壊れているエントリは
  合成した失敗スイート(`fleet-entry-missing` / `fleet-entry-unreadable`)として結果に残す。
  省くと CI からは「そのホストのぶんは全部通った」に見え、throw して1件も書かないと
  「JUnit が無い」= 設定次第で緑にも見える。**赤いテストが1件あるほうが確実に伝わる**。
  同じスイート名が複数ホストで出るので `hostname` を付け、合計は結合後に数え直す
  (各エントリの外側の合計を信用しない)
- デバイス選定は**実行プロファイルの devices が持つ `machine` で解決**する(devices 自体が
  すでにマシン単位の概念を持つ)

**machine 別見積りとディスパッチ固定費(2026-08-18)**: 機械ごとの速度差(手元と各リモート機で
異なる)とディスパッチ経路の固定費(SSH 接続・転送・増分ビルド)を割り当てに織り込む
(`FleetSplit.MachineContext`)。`RemoteHostFactsStore`(`.fleetest/remote-hosts/<host>.json`)は
machine 識別子・実測固定費に加え **CPU モデル・論理コア数・直近 run の同時起動デバイス数**も
持つ。CPU 情報はディスパッチの到達性プローブ(`RemoteRunDispatcher.resolveLayout`)に相乗りした
`sysctl` の実測、machine とデバイス数は回収した実績レコード(`machine`/`worker`)由来 ——
書き手が違う(前者はプローブ、後者はレコード)ので、片方だけ取れなかったときも他方は上書きで
消さない。ローカル機の facts は**この機械のホスト名を鍵に・表示名 `machineAlias: "local"`** で
`RemoteHostFactsStore.saveLocal` の1箇所が書く(SSH プローブを経由しないので `MachineHardware.current()` を
直接使う)。呼ぶのは `FleetRunner.buildMachineContext` / `DeviceMachineRunner.assign` と、**手元の run の
たび**(`ProfileRunner.prepareEnvironment` = run / api run 共通・dry-run では書かない)。後者が無いと
手元1台だけの利用者には組が1度も書かれず、host → 表示名の読み替え(`api results` の `machines`・拡張の
テストセッション)が効かずに画面へホスト名が出て、「マシンの健全性」が `local`(ライブ)とホスト名(履歴)の
2行に割れる(`LocalHostFactsWiringTests`)。

見積りは**同一機の実績 > 混合中央値 × 速度係数(共通観測シナリオの比の中央値)>
コア数の逆比(ローカル基準の事前係数)> 1.0** の順で決める。実績の無い機械には、
共通観測が貯まるまでの間 `entryFallbackFactors`(ローカルのコア数 ÷ 相手のコア数)を暫定係数として
使う ―― 観測が増えて速度係数が求まり次第、そちらへ自然に置き換わる(FleetSplit の優先順が
決める。facts に coreCount が無ければ 1.0 = 従来どおり均等)。**初回(キャッシュ無し)は
従来と同一の混合見積り**に退化する —— facts が無いエントリは machine=nil・offset=0・factor=1.0
として扱われる。**実績が1件も無い run は ms の固定費だけを落とす**(見積りが単位重みへ
退化するので、ms の固定費を同じ比較に載せると単位重みを支配してしまう)が、**コア数の逆比の
係数は効いたまま**にする(単位重み自体に掛かる比率なので単位を汚さない。
`FleetSplit.machineContext(_:ifHistoryExists:)` が offsets だけ 0 化して返す)。
**見積りはそのエントリが実際に回す platform の実績だけで作る**。同じ scenarioID を
ios と android の両方で走らせるプロジェクトでは、機械別の実績が片 platform に偏る —— ある機械が
直近 android でしか回していなければ、その機械の中央値は android のものになる。全 platform の
max を採ると、それが「同一機の実績」として ios の run へ入り、**速い platform の値で遅い
platform を見積もって、一番遅く終わる機械に最も多く配る**。実データ(受け手の iOS 98 本・3機・
18 レーン)では M1Ultra だけが android 由来の見積りを 9 本ぶん掴み、レーン当たり実績 552 秒に
対して推定 448 秒(−19%)で最後まで走る極になっていた(local +1% / M1Max +8%)。scope を掛けると
同じ入力で −7% まで縮む。**両 platform を回すエントリでは scope が両方 = 従来の max と同一**
なので、狭まるのは「そちらの platform を回せないエントリ」だけ。速度係数(`speedFactors`)も
**比の分子と分母を同じ platform で取る** —— platform を潰して割ると、速度差ではなく platform 差を
係数として掛けることになる。

ディスパッチのログは推定に続けて**その推定が何に基づいたか**を出す(`FleetSplit.EstimateBasis`。
`local: 43 scenario(s) on 8 device(s) [est. 485s; 36 from <machine> history, 7 scaled x1.00 (measured)]`)。
`--split` の割り当て表は BASIS 列。係数だけでは由来が分からず、遅い機に偏った run を後から
検証できない(2026-08-24 受け手要望)。

実行後の集計表には **IDLE 列**(そのエントリの最長 duration との差)がある —
静的割り当ての偏り(ストラグラー)を再配分機構を作る前に実測で貯めるためで、割り当てそのものは
実行後にフィードバックしない。効果の実測(3機械12台での収束データと、初回 run を効果の
基線にしない理由)は PT-3.7 の 7。

### RR-8.1 マシン間でシナリオを1本ずつ配る(動的な割り振り)

**実装と実測(2026-10-27)**: `DynamicSplit`(判定)・`FleetSplit.Estimator`(見込みの共有)・`WorkQueueProtocol` / `StdioPullSource`
(子の口)・`DynamicDispatcher`(親の配り手。`run` / `api run` が共有)。E2E-Flutter の ios-inapp-boost(28 本・手元 8 台 + M1Max 4 台 +
M1Ultra 6 台・実績あり)で静的と交互に 2 回ずつ: **全体 51.0 / 50.5 秒(動的)・51.8 / 53.8 秒(静的)**。実績がたまった run では
見込みどおり数%。初回(実績なし)・ばらつきの大きい run での効果は未計測。実地で踏んだ罠: ssh を包む sh(`ParentBoundCommand`)が
`&` のコマンドの stdin を /dev/null に付け替え、返事がリモートへ届かずリモートのデバイスが止まった(fd 3 へ退避して渡す。
`ParentBoundCommandTests.testStdinReachesTheWrappedCommand`)。stdin の横取り: stdin を指定せずに起こす子プロセス(adb・ssh など)が親の返事を読み、レーンがシナリオを受け取れず止まった(子の `WorkQueueStdin.claim()`)。その修正の直後、中継役が fd 0 を ssh へ渡していたためリモートへ返事が届かない退行が出た(中継は claim の fd を渡す)。いずれも本節の「親と子の間の口」と中継の記述を参照

**目的**: 1つの実行プロファイルのデバイスが複数のマシンにまたがる run(RR-13 の `DeviceMachineRunner` と、`api run` の対
`ApiRunMachineFanout`)で、最初に決め打ちする割り振り(上の LPT)をやめ、**空いたデバイスが親から次のシナリオを1本ずつもらう**。
初回(記録なし = 均等割りで最大 134 秒遊んだ)・短い run(最大 23〜32 秒)・所要のばらつきが大きい run の遊びを消す。
マシンの中のデバイスへの割り当て(`RunOrchestrator`)と同じ考え方を、マシンの間へ1段上げる。DR-103: 案 A。

**割り振りの規則(DR-103)**: あるマシンのデバイスが空いたら、待っているシナリオごとに
「**今このデバイスに渡したときの終わる時刻**(今 + このマシンでの見込み)」と「**同じ platform の他のレーン(他のマシン + 同じマシンの他のデバイス)に回したときの一番早く終わる時刻**
(そのデバイスが空く見込みの時刻 + そのマシンでの見込み)」を比べ、前者が後者以下のシナリオだけを渡す。比べるときは**他のレーンに控えている分も数える** —— 待っているシナリオを全部、見込みの長い順(LPT。`--no-lpt` は親の候補の順を ID 順にする —— 子のカタログの並びは配る順に効かない)に「一番早く終わるレーン」へ仮に積み(同着は要求したレーン)、要求したレーンに最初に積まれたものを渡す(`FTCore.BacklogPlacement`。TargetSchedule と共有)。
1本ずつ「他のレーンの次の空き」とだけ比べると、速いレーンの控えの山を前に遅いレーンが待ち続ける(実測は PT-8.1)。
1本も積まれなければ**何も渡さず待たせる**(遅いマシンが終わり際に長いシナリオを取って全体を引き延ばさない)。
- 見込みは今の静的な割り振りと同じ材料(`FleetSplit.MachineContext`: 同一機の実績 > 混合中央値 × 速度係数 > コア数の逆比)。
  **新しい記録の仕組みを作らない**。送りの固定費は run の開始で1回払い済みなので、ここでは足さない
- 比べる相手は要求を1度でも出したレーンだけ(供給中のレーンは空きと数えない)
- 「空く見込みの時刻」= そのデバイスが今回しているシナリオの開始時刻 + そのマシンでの見込み。空いて待っているデバイスは「今」
- **安全弁**: 比べた相手のデバイスが見込みの時刻を過ぎても空かなければ、相手の空く時刻を `今 + 超過した時間` とみなす(超過した分だけ後ろへ倒す)。比べ直す時刻は `reconsiderAt` で返し、要求・終わりの知らせ・その時刻のタイマーで判定し直す
- **端の条件**: 待っているシナリオがそのデバイスの OS で回せないものだけなら「もう無い」を返す(そのデバイスは終わる)。全部配り終えたら
  全デバイスへ「もう無い」

**親と子の間の口**: 子の run の標準入出力を使う。**子は run の入口で `WorkQueueStdin.claim()` を最初に呼ぶ**(stdin を close-on-exec の fd へ移し、fd 0 を /dev/null にする)。移さないと、stdin を指定せずに起こす子プロセス(adb・ssh など)が親の返事を読んで横取りし、渡したはずのシナリオをレーンが受け取れずに止まる(2026-10-27 実測: 手元で 28 本中 4 本・リモートで 5 本が結果なし)。`WorkQueueStdinWiringTests`:
- 子は新しい内部の口(`--work-queue`。利用者向けではない)で起こし、**全候補のシナリオを知った上で、配られた分だけ回す**
  (ビルドと一覧はふだんどおり)。デバイスが空くと **`{"ftWork":…}` の1行 JSON**(要求 `want`)を stdout に出し、
  stdin から1行の JSON(渡す/もう無い/見直して聞き直す `again`)を読む。待たせる = 親が返事を遅らせる。
  同じ口に run メモ(DR-208)・対象外の問い合わせ `na` と返事 `verdict`・回し直し中の知らせ `kept`(DR-214)・開始/取りやめ(RR-8.4)も載る
  (行の種類の一覧は `WorkQueueProtocol.swift` の冒頭が正典)
- 親(`DeviceMachineRunner` / `ApiRunMachineFanout`)が全マシンの要求を1か所で受け、上の規則で答える。`{"ftWork"` で始まる行は表示・NDJSON の
  中継から抜く(利用者には見せない)
- リモートの子は `ssh -tt` の先にいる: 中継役の `fleetest run --runner M --work-queue` は **`WorkQueueStdin.claim()` の fd** を ssh の stdin に渡し(fd 0 は入口で /dev/null に差し替え済みなので、fd 0 を渡すとリモートに返事が1本も届かず、リモートのレーンが全部止まる。それ以外の ssh(結果の回収など)は /dev/null のまま)、リモートの
  fleetest は stdin が端末なら**エコーを切る**(`tcsetattr`。切らないと送った行が出力へ折り返す)。行は端末の1行の上限(MAX_CANON)より
  十分短い(シナリオ ID 1つ)。**`-tt` はやめない**(手元の中断をリモートへ SIGHUP で届ける役 = RR-3)
- 却下した口: ssh の逆向きのポート転送(リモートの loopback に待ち受けが増え、同じ機械の他の利用者から届く = 認証が要る)/
  何回かに分けて run を送る(1回ごとに送りの固定費を払う = 案 B。記録がたまった run ではむしろ遅い)/ 常駐の中継デーモン(RR-2 の B)

**変えないもの**: `--broadcast`(全デバイスで全シナリオ)・`--fleet`(エントリごとに別のプロファイル。`--split` は今の静的な割り振りのまま)・
マシンの中のデバイスへの割り当てと再キュー(`RunOrchestrator` の `requeue`)・dispatch.lock の取り方(`DispatchPrelock`)・
結果の回収と JUnit の結合・`api run` の利用者向けの NDJSON(イベントの種類と形。`fleetestProtocolVersion` は上げない =
親子の口は同じ版の fleetest 同士の内部の約束で、リモートは適合チェックで同じコミットに揃っている)。

**中断**: 親は配るのをやめ、保留中の要求にも以後の要求にもすべて none で答える。子も中断を受けたら親の返事を待たず、待っている要求を全部 nil で終える(`ScenarioPullSource.stopWaiting`。`RunOrchestrator.requestInterrupt`)—— 親の返事が届かないレーンは、これが無いと中断しても解けない。
配っていない分は「中断で渡さなかった」と1行出し、失敗にはしない。

**落ちたマシン**: 子が途中で終わったら、そのマシンへ渡して終わりの知らせが来ていないシナリオは**回し直さない**(途中まで走ったかもしれない
= サーバーの状態を変えたかもしれない。届いたか分からない操作を撃ち直さないのと同じ規律)。今と同じく `reportMissingResults` の
「結果の無いシナリオ」として赤で残す。まだ誰にも渡していないシナリオは、残ったマシンへふつうに配る。

**既定と殺しスイッチ**: マシンをまたぐ run は既定でこの方式。保守者の殺しスイッチ環境変数 `FT_STATIC_SPLIT=1`(`DeviceMachineRunner.dynamicSplitEnabled`)で今の静的な割り振りへ戻す
(`FT_EMPTY_DRAG=off` と同じ位置づけ・利用者向けの口ではない)。

確かめ方: 純粋関数のテスト(`DynamicSplit` / `TargetSchedule`)・偽の源のテスト(`StdioPullSourceTests`・`PulledDispatchTests`)・配り手のテスト(`DynamicDispatcherTests`・`MultiTargetRunnerTests`)

### RR-8.2 複数の対象を1回で回す(run を丸ごと配る段とシナリオを配る段の統合)

**目的**: 回帰のまとめ役(`Scripts/regress.py`。PT-8.1)の良いところ —— **複数の run を1つの待ち行列で配り、run ごとの固定費を
マシンが並列に払う** —— を製品へ取り込み、RR-8.1(シナリオを1本ずつ配る)と1つの配り手にまとめる。DR-104:
口は `--profile` の繰り返し・終わり際はシナリオ単位へ切り替える・regress.py は薄い包みにする。

**口**: `fleetest run --project A --profile ios --profile android` / 複数のプロジェクトは `--target A:ios --target B:android`
(`--project` / `--profile` と併用しない)。**対象が1つなら今までと同じ経路**(RR-8.1 を含む)。2つ以上の対象は `--broadcast` `--fleet` `--runner` `--dry-run` `--scenario` `--folder` `--failed` `--port` `--platform` `--serial` `--app-id` `--device` `--device-machine` `--all-machines` と併用しない(一覧は `MultiTargetRunner.firstRejection` の呼び手 = `Fleetest.swift` の validate)。`--runner local` で絞れないので、regress.py は各プロファイルに載っている全マシンを使う。
`api run` には入れない(拡張は1プロファイルずつ起こす。理由は `RunCommandFlagParityTests` の表へ書く)。

**仕事と粒度**: 仕事 = 対象1つ(コードの語は target。run の上の「ジョブ」= DS-18.11 とは別物)。どのマシンで回せるかはそのプロファイルのデバイスの `machine` で決まる。**マシンは同時に1つの子 run だけ**
(1台1本 = dispatch.lock)。子 run は最初から `--work-queue`(RR-8.1 の口)で起こし、その仕事の候補を全部知った上で1本ずつもらう。
- 空いたマシンの次の仕事(`TargetSchedule.decide`。純粋関数):
  1. **まだ誰も始めていない仕事**: 「今このマシンで始めたときの終わる時刻(固定費 + そのマシンで全部回す見込み)」と
     「他のマシンに回したときの一番早い終わる時刻(そのマシンが空く見込み + 固定費 + 見込み)」を比べ、前者が以下なら始める
     (RR-8.1 と同じ規則を仕事の単位へ上げたもの = 遅いマシンが終わり際に長い仕事を取らない)。RR-8.1 と同じく**他のマシンの控えも数える**:
     未着手の仕事を全部(このマシンで回せない仕事も = 他のマシンを塞ぐ)見込みの長い順に一番早く終わるマシンへ仮に積み、このマシンに最初に積まれた仕事を始める。
     1本も積まれなければ待つ
  2. **このマシンで回せる**未着手の仕事が無いとき(終わり際)だけ、走っている仕事に2台目以降として**加わる**: 加わると、その仕事の残りが終わる見込みが
     早まる仕事のうち、早まる量が一番大きいもの。早まらなければ待つ。見込みは配る側(RR-8.1)と同じく**シナリオを1本ずつ仮に積んで**出す
     (`TargetSchedule.joinGain`。担当のデバイスは今・加わるデバイスは固定費の後に空くとみなす)。加わるデバイスに1本も積まれなければ加わらない ——
     量を割れるものとして速さの和で見ると、固定費を払って加わったのに速い担当が先に全部取り、1本ももらえないまま子 run の後始末のぶん全体の終わりを延ばす
     (実測は PT-8.1)。担当にも加わる側にも回せない platform のシナリオ(他のマシンの担当分)は積まない
  3. 始めていない仕事も、残りのシナリオがある走っている仕事も無ければ、そのマシンは終わり
- 仕事の中のシナリオは RR-8.1 のまま(仕事ごとに `DynamicDispatcher`。加わったマシンのレーンも同じ規則で比べる)。子は自分の仕事の
  残りが無くなると終わり、そのマシンは空いて次を選ぶ
- 「空く見込み」= min(始めた・加わったときに覚えた終わる時刻, 今 + 残りの見込み)。見込みを過ぎても空かなければ RR-8.1 と同じ安全弁
  (超過したぶん後ろへ倒す)。**「今 + 残り」だけにしない** —— 毎回いまから作り直すと遅れても期限を過ぎた側へ倒れず安全弁が効かない
  (2026-10-27 の実測: FM が落ちて遅くなった手元を空いた2台が10分以上待ち、未着手の対象を取らなかった)。残り = まだ誰にも渡していないシナリオの見込みの和 ÷ レーン数を、担当マシンの速さで合算したもの(走っているシナリオは数えない)。配っていない分が無ければ「今」。記憶した時刻は仕事ごとに1つで、始める・加わるたびに小さいほうへだけ更新し、担当が0台になって未着手へ戻した仕事は消す

**見込み**: シナリオは `FleetSplit.Estimator`(RR-8.1 と同じ)。仕事 × マシンは「そのマシンのその仕事のデバイスだけで、残りのシナリオを
全部回す時間」= 見込みの和 ÷ レーン数。固定費は `RemoteHostFacts.dispatchOverheadSeconds`(RR-8 の固定費)。新しい記録の仕組みは作らない。

**準備**: 対象のプロジェクトを手元でビルドして一覧を出す。ビルドが要るプロジェクトが2つ以上あれば1回の素の `swift build` でまとめて作る(`ScenarioHost.buildTogether`。swift build は起こすだけで 7〜13 秒払うので、1本ずつだと本数ぶん払う。まとめたビルドが失敗したら1本ずつに戻して、壊れたプロジェクトを名指しする)。リモートの子は今までどおり自分のプロジェクトだけを作る(ランナー機の作業フォルダは利用者側のパッケージで、まとめたビルドが無関係の壊れたプロジェクトで失敗する。実測は PT-8.1)。dispatch.lock は、残った仕事が使う全マシンぶんを(一覧が空で飛ばした対象だけが使うマシンは取らない = `MultiTargetRunner.labelsInUse`)
`DispatchPrelock` で最初に取り、全部の仕事が終わるまで持つ(途中で手放すと他人の run が割り込み、配り手の見込みが崩れる)。

**落ちたマシン・中断**: RR-8.1 と同じ(渡したシナリオは回し直さない・中断は待っている要求へ none)。落ちた = 子の終了コードが 0・1 以外。落ちたマシンには以後仕事を配らない。同じ (仕事, マシン) の子は1回しか起こさない(配り手は抜けたエントリの要求に答えないので、起こし直しても返事が来ない)。**担当が0台になった仕事に誰にも渡していないシナリオが残っていれば未着手へ戻し、ほかのマシンが始める**(戻さないと落ちた1台の残りが誰にも配られなかった)。中断以外で配られなかったシナリオや、どのマシンでも始まらなかった対象は赤。中断で残った分は失敗として記録しないが、親の終了コードは 130(子が全員 0 でも 0 にしない = 未実行を含む回帰を検証済みにさせない。3経路が `DeviceMachineRunner.parentExitCode` を共有)。「残った分」には**渡したのに結果が無いシナリオ**も入る(配り手は返事を送る前に pending から外すので、子が受け取る前の中断では未配布にも子の失敗にも数えられない)= run は結果 JSON の走査(`reportMissingResults` の戻り値)、api run は多重化の `unfinishedTotal` で数え、中断なら 130・中断でなければ 1。窓なしの照合し直し(全月の run.json を読む = 数千件で数秒)は、1つのプロセスの中で (結果フォルダ, runGroup) ごとに1回だけ読む。中断時の子の `stopWaiting` は RR-8.1 と同じ。**中断のあとは子を起こさない**: 起動の予約はロックの中・起動は外なので、起こす直前に中断を見て予約を戻す。起動から中断の登録(`FleetRunner.runEntry` の `InterruptRelay.forwarding(…, catchUp: true)`)までの間に来た中断は、登録と同じ臨界区間で「登録より前に中断を受けていたか」を見て、その子へ1回だけ伝える(登録の後で印を見ると forwardToAll と二重に送り、子の2回目の中断は後始末を飛ばして即終了する)。**配り手の購読も同じ**: ロックの取得中の中断は DispatchPrelock の購読が受けて終わるので、3経路の配り手(複数対象・run の機械分担・api run の機械分担)は `InterruptRelay.observing(catchUp: true)` で登録し、登録より前の中断を登録の直後に1回受ける。api run は自前のシグナルソースを持たない(過去の中断を知らない)。**3経路の親は入口(チケットの発行・手元のロックの先取りより前)で中断の印 `DeviceMachineRunner.ParentInterrupt` を立てて最後まで持つ** —— 先取りの `acquire()` は自前の購読を外すと既定動作へ戻すので、無いとビルドの間の SIGTERM で親が後始末なしに死ぬ。手元のロックの待ち・ビルド・一覧取得・手元のデバイスの使用中の待ち・配り手の登録の直前の中断は子を1つも起こさずに 130 で抜ける(`interruptedBeforeAnySubRun`。ビルド中の中断はビルドが終わってから拾う。言うのは「どの段で気づいたか」だけ)。**2回目の中断で即座に終わる逃げ道は置かない**(後始末を飛ばすと手元のロックが死んだ pid のまま残り、回収できるのは同じ利用者の次の run だけ = 強制終了と同じ結果)。DispatchPrelock から呼ぶ手元・リモートのロックの待ち(`LocalDispatchLock.acquire` の自前の購読・`acquireDispatchLockAsParent`)も catchUp(登録より前の中断で待たない)。`DispatchPrelock.acquireInOrder` は全部取り終えた直後にも中断を見る(最後の1台の取得の最中の中断を見ずに true を返すと、子を起こしてから止めた)。

**一覧と対象外**: 対象ごとの一覧は通常の入口と同じ `ScenarioSelection.resolve`(`@Draft` / `@Deleted` を外す)を通す —— 子へは完全一致の ID で渡すので子の側では外れない。外して空になった対象は飛ばす(全部の対象が空なら「nothing to run」。単機の入口は外して空なら断る = DR-213)。**レスポンス計測のプロファイルは複数対象と併用しない・単一対象でも動的に配らない**(反復 `responseRepeat` は子だけが展開し、親は同じ ID を1回しか配らない = 指定の回数を回さずに成功する。`--device` でリモートの1台に絞ると1グループでも機械分担の経路に入る。`dynamicSplitEnabled(measuresResponse:)`)。子も `--work-queue` と計測の併用を断る(run / api run の入口で stdin を移した直後 = 供給より前。`RunCommonOptions.rejectWorkQueueMeasurement`)。返事を待つ間に別のレーンが再キューした分は、返事が none でもそのレーンが拾う(`ScenarioQueue.next`)。

**regress.py の行方(実装済み)**: SUT の鮮度確認とビルドの段・回帰の対象の一覧(スイート × SUT × OS/モードの `--target`)・検証済みの印と推奨・
陽性対照・証人の run(`e2e.sh` の in-app の証人)・画像分類器の劣化の検査だけを残し、配る部分は `fleetest run --target …` へ任せる。
E2EX / E2EY のプロファイルにもリモートのデバイスを足す(E2E のプロファイルと同じ形)。


### RR-8.3 クラスを1台のマシン・デバイスへ寄せる(`@RunOnSingleMachine` / `@RunOnSingleDevice` / `@RunInOrder`)

決定は DR-206(属性と `@Order`)・DR-205(テストデータの置き方)・DR-207(メモ)。

**属性**(テストクラスにだけ付ける独立した印。`@TestClass` が展開時に読む = `TestClassMacro.hasDeleted` と同じ読み方。基底クラスの印は見ない。
3つとも省略できる理由の文を取る = `(_ reason: String = "")`):

| 属性 | 寄せる単位 | クラスの中 | 順番 | 失敗の後 | `--failed` |
|---|---|---|---|---|---|
| `@RunOnSingleMachine` | マシン(エントリ) | 並列 | 決めない | 続ける | 落ちた分だけ |
| `@RunOnSingleDevice` | デバイス(レーン)1台 | 1本ずつ・他のクラスを挟まない | 決めない(配り方のまま。関数名の順などに固定しない = 保証の無い順番に頼らせない) | 続ける | 落ちた分だけ |
| `@RunInOrder` | デバイス(レーン)1台 | 1本ずつ・他のクラスを挟まない | `@Order` の順(保証する) | 残りは実行せず赤 | クラスの最初から |

**前提(OS)**: OS を宣言していないテストは両方の OS で走るのではなく、run の既定の OS(iOS のデバイスがあれば ios)で1回だけ走り、キューは OS ごとに別。
「両 OS のクラス」= `@Test(platform:)` の ios と android が混ざった(または未宣言との組で2つの OS に解ける)クラス。
デバイスに寄せる2つの属性は1台のデバイス = 1つの OS でしか成り立たないので、OS の宣言がそろったクラスだけを受け付ける(下のコンパイルエラー)。

**コンパイルエラーにするもの**(マクロ。文言は英語 = DR-9): 3つの属性の2つ以上の同時付与 / 属性を `@Test` の関数・`@TestClass` の無いクラスに付けた /
`@Order` を `@RunInOrder` の無いクラスで使った(文言で、付け足す属性とそれで失うもの = 並列・失敗の後の扱い・再テストの範囲を言う)/
`@RunInOrder` のクラスに `@Order` の無い `@Test` がある(`@Order` は必須。関数名の順は `test10` < `test2`・日本語名で予想できないので暗黙の順番を持たない)/
`@Order` の値の重複 / `@Order` の値が整数リテラルでない(重複を検査できないため) / `@Order` を `@Test` 以外に付けた / デバイスに寄せる2つの属性のクラスで、テストの OS の宣言がそろっていない(全部が未宣言か、全部が同じ OS。クラスの `platform:` とメソッドの `platform:` を
合わせた実効の値で見る。未宣言と明示の組も断る = run の既定の OS しだいで通ったり断られたりする形を作らない)。

**run の開始時に断るもの**: `@RunOnSingleMachine` の両 OS のクラスに、
両方の OS のデバイスを持つエントリがプロファイルに1つも無い(文言にマシンごとの OS と対処 = `@TestClass(platform:)` で分ける・両 OS を1台のマシンにそろえる)/
`@RunInOrder` のクラスを、クラス全体でも先頭から連続した範囲でもない形で選んだ(`--scenario`・MCP の `ft_run_scenario`。run と api run の両方 =
`RunRejectionParityTests`)/ レスポンス計測の run に `@RunInOrder` のクラスがある(繰り返しの並べ方を決めていない。要る実例が出るまで断る)。
- 「先頭から連続」は、その run で実際に流れる並び(`@Deleted`・`@Draft`・その OS の対象外を除いた並び)で数える。途中の対象外は飛ばして続け、失敗と数えない。
  ID を明示して選んだ `@Deleted` / `@Draft` のテストは並びに含めて数える
- 拡張の木からの1本だけの実行・デバッグ実行も同じ入口(`api run --scenario`)なので、途中のテストは断られる(属性は一覧に出さないので、断る文言だけが手がかり =
  文言にクラスが `@RunInOrder` であることと選び方を必ず書く)
- `ft_run_scenario` は ID を1つしか取らないので、選べるのはクラス全体か先頭の1本。途中のテストを確かめるときはクラスごと流す(まだ書いていない後ろのテストは
  `@Draft`)と、断る文言で案内する
- dry-run(`--dry-run`・`ft_dry_run`)はデバイスを使わないので、選び方の制限・順番・失敗の後の扱いを掛けない

**実行時にエラーにするもの**(DR-208): テストメモの書き込み(`writeMemo`・`memoTextAs`・`clearMemo`)は `beforeAll()`・`setUpDevice()`・`tearDownDevice()`・`afterAll()`・`beforeRun()`・`afterRun()`、run メモの書き込みは `setUpDevice()`・`tearDownDevice()`・`afterAll()`・`afterRun()`。

**判定は1つの純粋関数に置く**(FTCore): 「どの順で渡すか・どこへ束ねるか・失敗の後に何を止めるか」を1か所に置き、呼び手は写すだけにする。呼び手は5つ ——
マシンの中のキュー(`ScenarioQueue`。共有キューは LPT 順なので、クラスを塊として扱い先頭のテストから渡す)・broadcast の割り当て(`BroadcastPlan`)・
親の配り手(`DynamicSplit` / `DynamicDispatcher`。複数対象の仕事ごとの配り手も同じ)と静的な割り当て(`FleetSplit.plan` = `--fleet --split`・`FT_STATIC_SPLIT=1`。
クラスを合計の見積もりを持つ1つの塊として置く)・CLI の1本ずつの実行・MCP の `ft_run_scenario`。

**束ね方**:
- デバイスに寄せるクラス(`@RunOnSingleDevice` / `@RunInOrder`)は、デバイスの台数を決めるとき1本として数える(`ResolvedProfile.scenarioCounts(_:)`)
- 寄せる先はコードに書かない(マシン名は手元の登録簿の別名 = RR-0)。クラスの最初の1本を受け取ったエントリ/レーンに束ね、以後そのクラスは他へ渡さない
  (`BacklogPlacement` の cost を他の担い手で nil にする)。供給を終えて先に要求したレーンに寄るので、遅れて合流するデバイスを待たない
- `@RunOnSingleMachine` の両 OS のクラスは、プロファイルで両方の OS のデバイスを持つエントリにだけ束ねる。供給の失敗で片方の OS のデバイスが
  合流しなかったら、その OS のメンバーは渡されなかった赤になる(既存の「渡されなかった」の行と、束ねた先が終わった分の行。専用の文言は持たない =
  合流しなかったデバイスは供給の段のログが言う)
- 複数のマシンに分かれる run では、束ねた瞬間に寄せた先を実行ログに1行出す(例: `OrderTests: kept on M1Ultra (@RunOnSingleMachine)`。
  `DynamicDispatcher`)。1台のマシンの中で束ねたとき・静的な割り当てでは出さない。属性は一覧(拡張の木・`ft_list_scenarios`)に出さない
  (`fleetest api` の契約を変えない)。`ScenarioInfo` へは必須の欄として載せる(同じビルドの子 → 親だけ = `beforeAll` の欄と同じ扱い)
- `--broadcast`・`--fleet`(`--split` なし)は断らない。`--broadcast` は3つの属性とも「この実行の形ではクラスが複数のデバイス(マシン)で同時に走る」と1行出す
  (`--fleet` は出さない = 発行側でシナリオの一覧を作らずビルドも飛ばす経路で、属性を知る材料が無い)
  (broadcast は全デバイスが同じクラスを流すので、同時に走らせない・データを1つにする目的は守られない。`@RunInOrder` のデバイスごとの順番は守る)。
  複数対象の run は対象ごとに別の run として寄せる
- 複数対象の run の「担当が0台になった仕事を未着手へ戻し、ほかのマシンが始める」(RR-8.2)から、束ねた先が落ちたクラスの残りを外す(戻すと別のマシンへ渡る)。
  仕事の終わりの判定(`dispatcher.pendingScenarios.isEmpty`)と、加わるかの見込み(`TargetSchedule.joinGain`・「空く見込み」の残り)も、他のマシンに束ねた分を
  数えない(数えると、1本ももらえないマシンが固定費を払って加わる・落ちたマシンの残りで仕事が終わらない)
  (実装の差: 加わるかの見込みは、終わったエントリに束ねた分だけを除き、**生きている他のマシンに束ねた分は数えたまま**。見込みの関数が
  マシンを引数に取らないため。結果は変わらず、加わったマシンが何ももらえずに終わることがある、という効率だけの差)

**離脱・復帰・振り直し**(実機は切れやすい。離脱したレーンは同じ名前で復帰を試み、復帰はアプリのデータを消さない):

| 属性 | レーンが離脱したら | 振り直し(`environmentFault` / `driverUnreachable` / 凍結) |
|---|---|---|
| `@RunOnSingleMachine` | 同じマシンの他のデバイスが続ける | そのマシンのどのデバイスでもよい |
| `@RunOnSingleDevice` / `@RunInOrder` | 復帰を待ち、復帰できたら走っていたテストをその場で流し直して続ける。復帰を諦めたら、走っていたテストは赤・残りは実行しなかった赤(他へ移さない) | その場で同じデバイスで、次へ進む前に(`avoiding` の別レーン優先を掛けない) |

- 振り直しの上限は今のまま(`MAX_FREEZE_RETRIES` = 1本につき1回)。復帰の上限も今のまま(`MAX_WORKER_REVIVES` = 1デバイス2回)。復帰の口が無い実行
  (プロファイルを通らない `--port` 直指定など)では、離脱 = 復帰を諦めた、と同じ扱い
- **デバイスに束ねたクラスを別のデバイスへ束ね直さない**(`@RunOnSingleDevice` も)。離脱したレーンで走っていたテストはそのマシンの中の別のレーンが拾って
  流し直す作りで、残りを親が別のマシンのデバイスへ束ね直すと、流し直しと残りが2台で同時に走る。親の配り手はレーンの離脱を知らない(レーンを知るのは要求が
  来たときだけ)ままでよく、束ねた残りは子が終わった時点で渡されなかった赤になる(親子の口に行を足さない)。走っていたテストの流し直しも、束ねたクラスの分は
  別のレーンへ渡さず、復帰したそのレーンだけが拾う
- 束ねた先のマシンが落ちたら(子が終わった)、残りを他へ移さず渡されなかった赤にし、文言に「この属性のため他へ移さなかった」と書く
- `@RunInOrder` の実行しなかった赤は、既存の「始まらなかったシナリオを失敗として残す」口(`RunRecorder.recordSkipped`)で記録し、理由に「前のテスト <ID> が
  失敗したので実行しなかった」と事実だけを書く(対象外 = notApplicable にしない)。この赤は連続失敗でレーンを
  離脱させる数え(`WorkerCircuitBreaker`)に入れない(1本の失敗で健全なデバイスが離脱する)

**利用者向け docs に書く限界**: どの属性も必要な場合だけ使う(DR-206)。`@RunOnSingleDevice` が防ぐのはそのクラスの中の同時実行だけ(同じアカウントを別のクラスも
使えばぶつかる。シナリオごとに別のアカウントを使う案内と合わせる)。

**束ねる前の見込み**: まだ束ねていないクラスは、1本ずつでなく塊で比べる。マシンに寄せるクラス = 残りの見込みの和 ÷ そのエントリの(その OS の)レーン数・
デバイスに寄せるクラス = 残りの見込みの和(1台で流すので割らない)。最初の1本だけで比べると、遅いマシン・デバイスが大きなクラスを取って全体を延ばす。
静的な割り当ても同じ値を塊の重さに使う。

**レポート**: `@RunInOrder` のテストのレポートに、クラスの中の実行順(何本中の何番目)を出す。一覧(拡張の木・レポートの目次)の並びは ID 順のまま変えない
(並びの規則を属性で変えると、他のクラスと並び方が食い違う)。

`@Order` と利用者の `Order` 型の名前の衝突は起きない見込み(同じ形で確かめた: Observation の `@Observable` マクロと同名の `struct Observable` を
同じファイルに置いて、属性としての使用も型としての使用も型検査が通った)。実装の後に FTDSL の実物で1回確かめる。

確かめ方: マクロの検査・判定の純粋関数・離脱と復帰と振り直しの扱いを単体テストで固定し、規則を外す変異で落ちることを確かめる(離脱と振り直しは緑の run で通らないので
偽の離脱を注入する)。陽性対照: 手元と M1Ultra にまたがる run で、属性の付いたクラスが寄る・外すと分かれる(陽性対照のクラスは1つの SUT だけに置く)。
実機を含む run で `@RunInOrder` が順に流れること・両 OS の `@RunOnSingleMachine` が断られるか寄ること(iPhone 13 か SE3)

### RR-8.4 run 全体の準備・片付け(`beforeRun` / `afterRun`)—— 第1段

**状態: 実装済み(第1段。2026-11-20)**。決定は DR-209。未実装で残したもの: なし(ロックは第2段 = RR-8.5)。**既知の穴(2026-11-20 のコードレビュー)**: デバイスが全部リモートにある run では、発行元は手元の dispatch.lock を持たないので、`beforeRun` / `afterRun` は手元の別の run と重なりうる(重なりの警告は出る。フックはデバイスに触らない)。run メモ(DR-208)の正本(`RunMemoHub`)と親子の通り道
(`--run-memo-link` / `--work-queue` の `{"ftWork":…}` の行)を土台にする。2026-11-20 の敵対的レビュー2回を反映した版。

**範囲**: **1回の run × 1つのプロジェクト**。複数の対象を1回で回す run(`--target` / `--profile` を並べる形 = RR-8.2)でも、同じプロジェクトの対象は
`beforeRun` / `afterRun` を1回ずつ走らせ、run メモの正本も1つにまとめる(`MultiTargetRunner` が対象ごとに作っている `RunMemoHub` をプロジェクトごとにする。
まとめた正本が子を見分ける鍵は **(対象, エントリ番号)**。エントリ番号だけだと、別の対象の同じ番号の子が終わったときに走っている子が配り先から外れる)。
別のプロジェクト・同時に走る別の run の間では共有しない。`--fleet` は発行元と各マシンの子がつながっていない(`FleetRunner.runEntry` に stdin も行の横取りも
渡さない = `--split` の有無に関わらない)ので、**`@RunHooks` があるプロジェクトの `--fleet` は開始時に断る**(各マシンでばらばらの時刻に走ると、共有サーバーの
初期化が他のマシンの run の最中に撃たれる)。**シナリオが0本の run では走らせない**。

**第1段の範囲は絞ってある**(2026-11-20。敵対的レビュー4回で、取りこぼした `afterRun` の回収と、終わりを確かめる口が毎回新しい穴を生んだため):
`afterRun` は `afterAll` と同じく「走れたら走る」で、取りこぼしを後で回収する仕組みは作らない。

**絞った規則**:
- `afterRun` は、全マシンの子が**正常に(終了コード 0 / 1 で)**終わったときだけ走らせる。いずれかのマシンの子が異常に終わった(切断・強制終了 = 向こうの run の終わりを
  確かめられない)・run が中断された ときは走らせず、「afterRun did not run: <理由>」を1行出す(向こうでまだ動いているテストの下で片付けを撃たない側に倒す)。控えも回収も作らない
- 開始の行: 各子について「起動の知らせ(`memoHello`)を受けた」と「`beforeRun` の結果が出た」の**遅いほう**で、その子の列へ「履歴 → 開始(または取りやめ)」の順に積む
  (hub の join と同じ臨界区間)。子は起動の知らせを入口ですぐ出す(ビルドと供給より前)。開始を待っている間も中断と親の死で解ける
- 取りやめを受けた子は、理由付きで自分の run の結果(run.json の abortReason)に書き、終了コード 1 で終わる(配り手はこの子を dead と数えない)。
  複数の対象の run では、`beforeRun` が失敗したプロジェクトの対象だけを止め(以後起こさない)、別のプロジェクトは続ける
- `beforeRun` / `afterRun` には、どの構成でも compose のテスト用サーバーへの通り道を渡さない(1台では届き複数台では届かない、という形を作らない)
- 時間の上限は、その run のそのプロジェクトの対象のうち最も長い `scenarioTimeout`
- MCP の `ft_run_scenario` も走る場所に含め、run と同じ判定(関数)を共有する

- 書き方: `@RunHooks` を付けたクラスに `func beforeRun()` / `func afterRun()`(片方だけでもよい)。`@TestClass` と同じクラスには付けない(コンパイルエラー)。
  プロジェクトに2つ以上あれば、一覧を作った時点(run の開始前・dry-run も)で英語のエラーにして止める
- 走る場所: スケジューリングを行うマシン(発行元 = `DeviceMachineRunner` / `ApiRunMachineFanout` / `MultiTargetRunner` の親)で、シナリオ実行バイナリを
  専用の口(例: `--run-hook before|after`)で起こす。入口は `ScenarioHost.sandboxedLaunch`。1台のマシンだけの run ではその run の親。
  **1台のリモートへ丸ごと配る run(`run --runner <機>`)はランナー機の run の親**(手元はビルドも割り振りもしない。設定もランナー機のもの)。
  **親とつながった子(`linkedToParent` = `--work-queue` / `--run-memo-link`)は走らせない**。`run` と `api run` の両方の経路。
  どの場合も、run ログに「どのマシンで走ったか」を1行出す
- 順番: そのプロジェクトの最初のシナリオを、どのマシンへも渡す前に `beforeRun` を終える(デバイスの供給とは並行してよい)。`afterRun` はそのプロジェクトの
  全対象・全マシンの子が終わり、各マシンの `afterAll` が終わった後(走らせる条件は「絞った規則」)
- **順序の保証**: 発行元から子への行(割り振りの返事・run メモ・開始の行)は**子ごとに1本の直列の列**に通し、**列ごとに独立した書き手**(スレッドか直列キュー)が
  書く。子の stdout を読むスレッドは書かずに列へ積むだけ(読み手のスレッドが直接書くと、返事が書き込みを追い越しうる・双方向の pipe で止まりうる・1台が詰まると全部の子への行が止まる)。`beforeRun` の書き込みを列に積んでから
  開始の行と最初の返事を積むので、子は必ず書き込みを先に受け取る
- **開始の行**: 親とつながった子(`linkedToParent`)は、**発行元から開始の行を受けるまでシナリオを流し始めない**(動的な割り振りの子だけでなく、`--broadcast`・
  静的な割り振り・計測の子も。待たないと起動引数の一覧を供給が済み次第流し始める)。`beforeRun` が失敗したら、開始の行の代わりに**取りやめの行**を送り、子は1本も流さずに
  専用の終わり方で終わる(中断のリレーは使わない = 中断として記録しない)。`@RunHooks` が無いプロジェクトでも開始の行は送る(待つ側を1つの規則にする)
- デバイス: ドライバを持たずに起こす。デバイスを操作するコマンドは「beforeRun()/afterRun() cannot use the device」の英語のエラー(コマンド名を添える)。
  使えるのは run メモ・`httpRequest`・`data()` / `account()`・`wait`
- **走ったマシンの設定で動く**: `httpRequest` の宛先の許可(`sandbox.allowedDomains`)と、データセットのマシンごとの上書き(`~/.config/fleetest/dataset/`)は
  走ったマシンのもの。compose.yaml のサーバーもマシンごとのコンテナなので、`beforeRun` で入れたデータはそのマシンのコンテナにしか入らない。
  `beforeRun` は「全マシンが共有する外部のサーバー」と run メモの準備に使い、マシンごとの準備は `run-setup.sh` / `beforeAll` に置く(利用者向け docs に必ず書く)。
  走るマシンは付けたフラグで変わる(全台が1つのリモートにある run はランナー機・`--device` で絞って分割になれば発行元)ので、`beforeRun` が読んだ `data()` / `account()` に
  **そのマシンだけの上書きがあれば警告の1行**を出す(各マシンのシナリオが引く値と食い違いうる。禁止はしない = 値は run メモで配る形を docs で案内する)
- 失敗: `beforeRun` の失敗は**専用の終わり方**(中断とは混ぜない = 終了コード 1・abortReason に理由・シナリオは1本も流さず、`--failed` の対象にも記録しない。
  RR-8.2 の「中断以外で配られなかったシナリオは赤」と `reportMissingResults` の数えからも、この場合だけ外す)。
  デバイスの供給を並行で始めたマシンの子は取りやめの行で畳む。**`afterRun` は `beforeRun` が失敗しても走る**。`afterRun` の結果は合否に数えない
- 結果の残し方: `beforeAll` / `afterAll` と同じ口(run ログの1行・レポート・全体レーン `__overall__`)。`fleetest api` の NDJSON・結果 JSON に新しい形の行を足さない
- 時間の上限: 実行プロファイルの `scenarioTimeout`(新しい数字を置かない)。debug 実行でも同じ上限を効かせる
- run メモ: `beforeRun` の書き込みは正本に確定分として先に入る(通し番号の先頭)。正本は**中身が読めることを確かめてから**番号を振る(読めない断片の組に番号を
  振ると、受け手が捨てて番号が抜ける)。各マシンは起動の知らせ(`memoHello`)で履歴を受け取る。1台のマシンだけの run ではレーンを起こす前に共有の写しへ入れる。
  `afterRun` は全マシンの書き込みがそろった最終の値を読む。`setUpDevice()` / `tearDownDevice()` / `afterAll()` / `afterRun()` での run メモの書き込みを断る規則(DR-207)は残し、
  文言は「the tests have already finished. Write it in beforeRun() or in the tests instead」に直した(読む人がいないのではなく、テストが終わった後だから)
- MCP の `ft_run_scenario` も run なので、1本流すたびに `beforeRun` が走る。共有サーバーを初期化する `beforeRun` は、同じサーバーを使って走っている別の run を壊す、
  と docs に書く
- **別々の run**: 範囲の外(拡張が1プロファイルずつ起こす run を同時に回す・ターミナル2つ・MCP)では `beforeRun` が run ごとに走り、ロックも効かない。
  **同じプロジェクトの別の run と時間が重なったら開始時に1行出す**(実装: この機械の run の台帳 `~/.fleetest/runs` の生きた pid の記録で数える = `RunWideHookPlan.overlappingRunsLine`。ジョブの台帳 DS-18.11 は run をまとめる単位でプロジェクトの重なりを引けない。別のマシン・別の利用者の run は見えない)
- 発行元が死んだとき: 子は親の死の検知(`ParentDeathWatch`)で終わる。ssh -tt の先では stdin の EOF が当てにならないので、EOF を終わりの合図に使わない

確かめ方: 一覧の検査(`@RunHooks` が2つ)・走らせる判定(親とつながった子では走らせない・`run --runner <機>`)・失敗の終わり方・`afterRun` を走らせる条件(全マシンの子が正常に終わったときだけ)を単体テストで固定し、
変異で落ちることを確かめる。陽性対照: 手元と M1Ultra にまたがる run で `beforeRun` の書き込みを全テストの最初の1本から読めること・`afterRun` が最終の値を読めること・
同じプロジェクトを2つのプロファイルで回しても `beforeRun` が1回だけ走ること(E2E-CMP だけに置く)

### RR-8.5 run 全体のロック(`withRunLock`)—— 第2段

**状態: 段取り 2a の第1・第2ステップ(1台のマシンの run と、マシンをまたぐ run の手元の子)と、2b の第1ステップ(ssh の転送でリモートのマシンでも効かせる・持ち主不明のキー・シナリオの終わりの知らせ・確かめ直し)は実装済み。**2b の第2ステップ(待った時間の RemoteTimeout からの差し引き・結果 JSON の `lockWaitMs`・所要の見積りからの除外)も実装済み = 段取り 2b 完了**(ユーザー決定 2026-11-20: 設計の敵対的レビューを5回回した後、実装してからコードでレビューする)。決定は DR-210。**未実装: `run --runner <機>`(1台のリモートへ丸ごと配る run)の待ちによる RemoteTimeout の延長(聞く側の待ち受けが無い。下の「待ちを外す窓」)。陽性対照: 済(手元4台・手元 + M1Ultra。ロックなしの陰性対照も)。**既知の穴(2026-11-20 のコードレビュー)**: ssh の期限の延長はロックの待ちだけを数え、開始の行の待ち(`beforeRun` の所要)は数えない(`--remote-timeout` をぎりぎりに明示した run だけが打ち切りになりうる)。MCP の同時の呼び出しはプロジェクトごとにロックのホストを共有するが、`beforeRun` / `afterRun` は呼び出しごとでロックに守られない(利用者 docs に注記)。
**2a の作り(次に触る人向け)**: 発行元(`DeviceMachineRunner` / `ApiRunMachineFanout` / `MultiTargetRunner`。複数対象はプロジェクトごと)が、ソースがロックを使うときだけ `RunLockIssuer`(`RunLockServer` + backend = 発行元の `RunMemoHub`)を起こし、**手元の子(`--runner local`)にだけ** `--lock-socket` を渡す。受けた子は `RunLockHost` が `.issuer(path)` になり、シナリオはそのソケットへ直接つなぐ。ロックの中の書き込みは hub の `seedConfirmed`(確定として通し番号を振って全部の子へ配る)。**ロックの外の書き込みとの順序**は、シナリオ → 子の `RunDeviceSession.apply` → 子が hub へ行で上げ、hub が確定して配り返した行(自分の印の lid)を子が受けた時点で、子が発行元のサーバーへ `outsideApplied` を送る(ソケット経由 = 行の欠けと独立)。サーバーは `memoRead` / `memoWrite` の前に、シナリオが出した数に届くまで待ち、上限(その run の最長の scenarioTimeout)で英語の理由つきの失敗にする(行を失ってもハングしない)。範囲・順序の保証・`run --runner <機>` の扱いは RR-8.4 と同じ。
**2b 第1ステップの作り(次に触る人向け)**: 発行元のサーバーは**待ち受けを出どころごとに持つ**(手元用1つ + **リモートへのディスパッチ(中継役の子の起動)1回ごとに1つ**。出どころは受けた待ち受けだけで決める。持ち主不明の範囲もこの待ち受け = ディスパッチごと。機械で括ると、同じ機械の前の対象の不明を後の対象の「run が終わった」で外してしまう)。待ち受けは子を起こす直前に開き、子が終わったら閉じる(受けた接続と不明は残る)。中継役(`RemoteRunDispatcher`)は、発行元から `--lock-socket`(そのディスパッチの待ち受け = 識別子)と `--lock-control-socket`(手元の待ち受け)を受けたときだけ、今の ssh に `-o ExitOnForwardFailure=no`(利用者の ssh_config の yes に負けない)と `-R /tmp/ftlock-<8桁>.sock:<そのディスパッチの待ち受け>` を足し、向こうの run へ転送元のパスを `--lock-socket` として渡す。(`StreamLocalBindUnlink` はクライアント側の指定が `-R` に効かない = 向こうの sshd の設定なので頼らず、パスをディスパッチごとに一意にする)。向こうのマシンの親(`ScenarioHost`)は**シナリオのプロセスを見届けた(reap した)後に**同じ転送で `scenarioEnded(token)` を送る。サーバーはその印の接続が**閉じたとき**に持ち分を外す(接続の EOF はそれまでの全メッセージ = `release` の後に処理される。`scenarioEnded` が先に着いても、正常に放した分に「前の持ち主が接続を失った」印を付けない。閉じたまま持っていた分だけ印が付く)。リモートの待ち受けで受けた接続が外さずに閉じ、その印が未報告なら**持ち主不明**(表 `RunLockTable.markUnknown`。接続を閉じる処理は表から外す・印を残す・不明にするを1回の操作で行う)。ssh が終わったら中継役が手元の待ち受けへ `sshEnded(識別子)` を送り、サーバーは不明のキーの数と待ちの上限を返す。**不明のキーがあるときだけ**中継役が ssh の pgrep で向こうの run の終わりを確かめ直し(`RunLockRecheck`。間隔 2 秒・上限は待ちの上限 + 後始末の猶予 30 秒。発行元が接続を閉じる・不明が消える・**中断される**と止める。正常終了(0/1)で中断でなければ ssh を撃たずに終わったとする)、終わったら `remoteRunEnded(識別子)` を送ってサーバーがそのディスパッチの不明だけを外して印を付ける(以後その取得のステップに注記)。確かめ直しは中継役のプロセスの中なので、不明のキーが残る間は発行元がその子の終わりを待つ(上限つき)。
**2b 第2ステップの作り(次に触る人向け)**: ①**RemoteTimeout の延長**は stdout の行ではなくサーバーが数える(行は欠けうる)。サーバーはリモートのディスパッチ(待ち受け)ごとに、要求が行列に入ってから渡し・失敗・取り消し・接続の終わりまでの**和集合の壁時計**(`RunLockWaitUnion`。デバイス数ぶんの足し算にしない)を持ち、中継役の制御用の接続の `waitedQuery` に `waited` で答える。中継役(`runInheritedWithLineRewrite`。`dispatch` と `dispatchApi` が共有する。**延ばすのは発行元が `--lock-socket` を渡した多マシンの run の中継役だけ**)は ssh の期限に達するたびに累計を聞き、**前回までに延ばした分との差**だけ延ばす(`RemoteTimeoutExtension`)。新しい期限の起点は `max(いまの期限, いま)`・1回の延長は最小 5 秒(問い合わせの頻度の下限)・ログは最初の延長と最後の要約だけ(`RemoteDeadlineWait`)。延長の合計の上限は元の期限(根拠: ロックの待ちは run の壁時計の一部なので、見積りの全部をロックの待ちに使う run は詰まっている。数え続ける詰まりで無限に延びない)。接続が無い・切れたら延ばさず従来どおり打ち切る。②**結果 JSON**: シナリオのプロセスが行列に入って待った合計を `scenarioFinished` の `lockWaitMs` で親へ運び、`ScenarioRunRecord.lockWaitMs`(**省略可の `Int?`・0 より大きいときだけ書く**。欄が無い = 待った記録が無い、という意味を持つ欄なので互換の読み替えではない = DR-75。**既存の記録の移行は要らない** —— 必須にすると全機の記録の移行を忘れたとき履歴と LPT が黙って消えるため省略可にした。api NDJSON の契約は変えていないので ProtocolVersion は上げない)へ畳む。③**見積り**: LPT の並べ替え・動的な割り振り・残り時間(`RunProgressEstimate`)・フリート分割は `LPTScheduler.durations` / `machineDurations` の1箇所で中央値を作るので、そこで `durationMs - lockWaitMs`(`estimateDurationMs`。最小 1)を使う。
**段取り**: **2a** = 1台のマシンの run と、マシンをまたぐ run の**手元の子**で効く(リモートのマシンでロックを呼んだら「呼んだら失敗」= 黙って割れない)。
**2b** = ssh の転送でリモートのマシンでも効かせる(下の「つなぎ方」「持ち主不明のキー」の確かめ直し)。

**通り道はロック専用の接続**(ユーザー決定 2026-11-20)。親子の間の `ftWork` の行(stdout / stdin)には載せない —— その通り道は stdout と stderr が同じパイプや
pty で混ざり、PIPE_BUF(512 バイト)を超える行は他の書き込みと混ざり、端末のエコーがあり、行が黙って欠けうる。ロックのように「届いたか」が正しさを決める用途に
載せると、欠けのたびに永久の待ち・幽霊の持ち主・書き込みの消失が出た(設計の敵対的レビュー4回で毎回重大)。

- **書き方**: `withRunLock(_ keys: String..., waitSeconds: Double? = nil, body: () -> Void)`。本体は `Void` だけ(値を返す形を置かない =
  失敗の後に本体を実行しない、を守れる)。キーは1つ以上・空白だけはエラー・**制御文字(Cc。DEL を含む)はエラー**(キーは run ログ・失敗の文言・結果に出る)。
  キーの長さと個数に上限は置かない(DR-210)。検査は呼んだ時点で行う(`RunLockWire.swift`)。どのフェーズでも使える。MCP の `ft_batch` は受けない
- **取り方(デッドロックを作れなくする規則)**: 取ろうとした時点で判定し、違反は競合の有無に関わらず英語のエラー
  ①1回の呼び出しに複数のキー → **名前の順に1つずつ取り、取った分は持ったまま次を待つ**。名前の順は **UTF-8 のバイト列の比較**(Swift の `String` の比較は
  Unicode の正規化に依り、版の違うマシンの間で順番が割れうる)
  ②**入れ子は全面禁止**: ロックの中で `withRunLock` を呼ぶとエラー(キーが同じでも別でも・競合の有無に関わらず・dry-run でも。文言に「要るキーは全部1回の呼び出しで渡す」を書く)。
  1回の呼び出しの中の同じキーは重複を除く
  → 全員が同じ順番でしか待たないので、待ちの輪ができない(「全部そろうまで渡さない」形は、先着順との組み合わせで2者のデッドロックを作るので採らない)
- **待ち行列**: キーごとに先着順
- **ロックのサーバー**: 発行元(run の親。1台のマシンの run ならその run のプロセス、マシンをまたぐ run なら発行元、MCP の `ft_run_scenario` なら MCP サーバー)が
  unix ソケットで待ち受ける(`FTCore.AcceptLoop` を通す)。判定(規則①②・待ち行列・持ち主・持ち主不明)は FTCore の純粋な型1つに置き、サーバーとテストが
  同じ型を使う。ソケットのパスは短く一意にする(`sun_path` は 104 バイト。一時ディレクトリの下に run ごとの名前)。
  **待ち受けは出どころごとに分ける**(5回目の設計レビューの重大): 手元のプロセス用に1つ、リモートへのディスパッチ(中継役の子の起動)1回ごとに1つ(そのディスパッチの転送だけが指す)。機械ごとにしない = 機械ごとだと、後の対象の「run が終わった」が前の対象の持ち主不明を外してしまう(`RunLockHost.swift:418-420`・`RunLockIssuerSetup.swift:41-49`)。
  接続の出どころは**どの待ち受けで受けたか**で決め、相手の名乗りや pid に頼らない(リモートの run は自分を `local` と名乗り、転送越しの `LOCAL_PEERPID` は
  手元の ssh の pid になる = どちらも逆を向く)
- **つなぎ方**: 各シナリオのプロセスは**自分のマシンの**ソケットへ直接つなぐ(シナリオのサンドボックスは名指しした unix ソケットへの接続を許す =
  `ScenarioSandbox.Scope.helperSockets` に足す)。リモートのマシンでは、中継役が今の ssh に **unix ソケットの転送(`-R <向こうのパス>:<発行元のパス>`)**を足し(`-o ExitOnForwardFailure=no` を明示して渡す = 利用者の ssh_config の `yes` に負けない)、
  向こうのパスをリモートの run へ渡す。**ssh ごと落とさない**(ExitOnForwardFailure は付けない = 転送の失敗で run 全体を落とさない)。転送は**プロジェクトの
  ソースがロックを使うときだけ**張る(`withRunLock` の宣言の走査 = `RunWideHookPlan.sourceDeclaresRunHooks` と同じ形)。張れなかったら
  シナリオのプロセスはつなげないので、ロックを呼んだ時点で英語の失敗(黙って割れない)。
  接続は**シナリオのプロセスごとに1本**で、最初の1通に名乗り(シナリオ ID・マシン・デバイス・子の印)を載せる(持ち主の名指しに使う)
- **ロックの扱いの印**: 受け渡しの行(`DeviceSessionHandoff`)に**必須の欄**で載せる。値は4つ —— **ソケットのパス**(答える)/ **その場で渡す**(他と競合しない起動:
  `beforeRun` / `afterRun` = run に1つ・他のシナリオと時間が重ならない、debug 実行と debug の `--after-all-only` の子 = 1シナリオ・1台)/ **取らずに通す**(dry-run)/
  **呼んだら失敗**(`--fleet`・親とつながった子なのにソケットを渡されなかった・転送を張れなかった)。親とつながった子(`--run-memo-link` / `--work-queue`)は
  **発行元から `--lock-socket <パス>` を受けたときだけ**ソケットを載せる(受けていないのに1台の run の既定 = 自分でサーバーを起こす、へ落ちると、マシンごとに
  別々のロックになって誤った緑)。`--fleet` の印は手元の fleet のエントリの引数と `RemoteRunArgs.build` の両方で運ぶ。印を立てる経路の一覧(付け忘れを走査テストで落とす):
  1台のマシンの run と `api run`・マシンをまたぐ run の子・MCP `ft_run_scenario`・`--after-all-only` / `--device-teardown-only` の起動・計測の子
- **run メモとの組み合わせ**: **ロックの中の書き込みだけを接続で発行元へ送り、確定の返事を待ってから次へ進む**。ロックの外の書き込みは今の通り道のまま
  (全部を接続へ移すと、マシンの親が自分の帳簿に未確定として積めなくなり、同じマシンの次のシナリオから見える = DR-208 の保証が後退する。5回目の設計レビューの重大)。
  **ロックで守るキーはロックの中でだけ書く**、と docs に書く(同じキーをロックの外でも書くと、外の書き込みが後から届いて中の値を上書きしうる)。
  ロックの中の書き込みは発行元が hub の履歴へ確定させ、他の子へは今どおり行で配る(書いたマシンの次のシナリオからも、届いた後に見える)。**ロックの中の `readRunMemo` は接続で発行元の最新の値を聞く**(ロックを出た後もそれを見続ける)。
  ロックの外の `readRunMemo` は今どおり手元の写し(開始時点の写しと、届いた分)。**「外す」の返事は、それまでの書き込みが全部確定した後**に返る(同じ接続の順序で
  保証される = 行の欠けに依らない)。ロックの中で上限(`RunMemoWire.maxPieces`)を超える書き込みは、1台の run でもエラー。
- **待ち**: 取れるまで待つ。待っている間テストはその行で止まり、デバイスは他のシナリオに使われない。**待った時間は `scenarioTimeout` の締め切りから外す**
  (既存の延長の差し引き `WatchdogExtensionTracker` と同じ扱い。台数を増やすほど時々赤になる形を作らない)。
  **1回の呼び出しの待ちには絶対の上限 = その run の最も長い `scenarioTimeout`**(ユーザー決定 2026-11-20。`@Test(scenarioTimeout:)` も含める。値は発行元が一覧から
  求めて受け渡しの行で運ぶ。上限は呼び出し全体に効き、キーごとに伸ばさない)。`waitSeconds:` を渡すとその値(短いときだけ効く)。**上限はシナリオのプロセスが
  自分の時計で判定**し、超えたら接続へ取り消しを送って英語の失敗にする(返事を待たない。持ち主の名指しは、発行元が取り消しを受けたときに run ログへ出す)。
  取り消しと渡しがすれ違ったら失敗のまま(取れた扱いにしない)で、発行元は**既に渡した要求の取り消しを「外す」として扱う**。複数のキーを1回で取る途中で切れたら、
  取った分も外す。激しく取り合うと、台数を増やしたときにこの上限に当たりうることは docs に書いて許容する(重い排他は DB を使う)。
  シナリオのプロセスの側の待ちは、DSL のコマンドの締め切り(FTSync の 120 秒)の外に置く。取れたら待った時間をステップの記述に出す
- **待ちを外す窓**: 待ちの始まりと終わりは、シナリオのプロセスが今の NDJSON のイベント(子 → マシンの親。窓を開く・閉じる)で親へ知らせ、親は締め切りと出力の無さの
  打ち切り(`ScenarioIdleBudget`)・固まりの検知・遅いレーンの判定から外す(終わりの無い除外の窓を新しく設ける。既存の `WatchdogExtension` は始めに上限を要り、
  枠も1つ)。**窓は既存の `DeadlineExclusion` を使う**(上限 = 絶対の上限。`waitSeconds:` は窓を短くしない = 呼び出し側の待ちだけを短くする。終わりの無い窓は新設しない)(閉じるイベントが届かなくても外しっぱなしにならない)。リモートの run 全体の上限(`RemoteTimeout`)からも差し引く:
  発行元のサーバーがディスパッチごとに**待ったデバイスの和集合の壁時計**(`RunLockWaitUnion`)を数え、中継役が制御用の接続で問い合わせて、前回までの延長との**差**だけ延ばす
  (stdout の行は欠けうるので運ばない)。**`run --runner <機>` は延ばさない**(聞く側の待ち受けが無い。未実装)。待った時間は結果の `lockWaitMs` に残し
  (省略可の欄 = DR-75。版は上げない)、所要の見込み(LPT・動的な割り振り)からは差し引く。一定の間隔ごとに**発行元が** run ログへ「待っているキーと持ち主」を1行出す
- **失敗したとき**: 失敗は例外ではなく中断の印(`scenarioAborted`)なので、本体の Swift のコードは走り続ける。**印が立った後はロックの本体を実行しない**。
  本体の途中で印が立っても、**外すのはブロックを抜けた時点**(その時点で外すと、本体の残りの生の Swift のコードが次の持ち主と同時に走る。失敗の後の DSL の
  コマンドはどれも飛ばされるので、早く外す利得は小さい)。外す前に書いた分は確定する(途中の値が残りうる、と docs に書く)
- **持ち主のプロセスの終わり(接続の終わり)**: 接続が「外す」を送らずに閉じたら —— 待っていただけの接続は、その要求を消すだけ。持っていた接続は出どころで分ける。
  **手元の待ち受けで受けた接続** → 相手の pid(`LOCAL_PEERPID`。接続の最初に取って控える)の終わりを kqueue の `NOTE_EXIT` で待ってから外す(1回の生死の判定は
  終わりかけのプロセスを生きていると答えうる)。**リモートの待ち受けで受けた接続** → 「持ち主不明」(ssh の切断でも閉じ、切れた先でまだ臨界区間を走っていることがある)。
  **リモートのマシンの親もロックのサーバーへつなぎ**(同じ転送)、自分が起こしたシナリオのプロセスが終わったら(reap した事実)その接続で「このシナリオが終わった」を
  知らせ、発行元はそれを受けて外す(持ち主不明になるのは ssh そのものが切れたときだけ = シナリオ1本の打ち切りで全マシンのそのキーが赤に連鎖しない)。
  クライアントのソケットには `O_CLOEXEC` を付ける(シナリオが起こした長生きの子が fd を継ぐと、持ち主が死んでも接続が閉じない)
- **持ち主不明のキー**(ユーザー決定 2026-11-20): 不明な持ち主が持っているキーへの要求は、新しく来た要求も既に並んでいた要求も、待たせずにすぐ失敗させる。**向こうの run の終わりを確かめたら外す**: 中継役は ssh が終わった後、
  向こうの run が終わったか(`--report-dir` を引数に持つプロセスが残っていないか。リモートの `--report-dir` はディスパッチごとに一意)を確かめ、終わったら
  「終わった」を発行元へ知らせ(中継役も発行元のソケットへつなぎ、同じ接続で送る = 行に載せない)、発行元はそれを受けて外し、待っていた要求に渡す。
  確かめた結果は「run が終わったか」と「dispatch.lock を外したか」を別の値で返す(実装は `remoteRunHasEnded`。`RemoteRunDispatcher.swift:832-836`)。一度で確かめられなければ間をおいて確かめ直し、上限は**その run の最も長い `scenarioTimeout` に後始末の猶予を足した値**
  (決めた値: 確かめ直しの間隔 2 秒・後始末の猶予 30 秒。`RunLockControl.swift`)。確かめ直しは発行元の接続が生きている間だけ続ける(発行元は run の仕事が全部終わったら中継役の接続を閉じる = 中継役は
  確かめ直しをやめて終わる。まだ起こしていない仕事が残る複数対象の run では、発行元は残りがある間は閉じない)。上限まで確かめられなければ run の終わりまで
  持ち主不明のまま(外すと切れた先の臨界区間と二重に持つ)。**持ち主不明から外したキー**は印を持ち、以後そのキーを取ったステップに「前の持ち主との接続が切れたので、
  その書き込みが欠けているかもしれない」の注記を付ける(失敗にはしない)。**run の終わりはロックの状態に依存させない**(子が全員終わったら、持ち主不明のキーは
  持ち主不明のまま閉じる)。(クライアントは再接続しない = 外した持ち主の後続の要求は届かないので、世代番号は持たない)
- **発行元が先に終わったとき・接続が使えないとき**: シナリオのプロセスは接続の EOF・`ParentDeathWatch` の SIGTERM で待ちを失敗にして抜ける。
  ロックを呼んだ時点でつなげない(サーバーが居ない)ときは、待たずに英語の失敗
- **中断**: 発行元は中断を受けたら、待っている要求を全部失敗させ、**中断の後に来た新しい要求もすぐ失敗させる**
- **接続の書き込みと DR-136**: 書き込み・外すを送った後、返事の前に接続が切れたら撃ち直さずに失敗にする(届いたかもしれない = 値は入ったかもしれない旨を出す)。
  再接続はしない(切れたシナリオのロックは以後全部失敗)
- **MCP の `ft_run_scenario`**: 別々の呼び出しが同時に走りうるので、MCP サーバーのプロセスがプロジェクトごとにロックのサーバーを1つ持つ(`RunLockHost.mcpShared`)。同じプロジェクトの呼び出しは互いに排他される
- **振り直し・流し直し**: 振り直されたシナリオはロックの本体をもう一度実行する(カウンタは二重に足される)と docs に書く
- **dry-run**: ロックは取らずに本体を通す。入れ子(規則②)は dry-run でも出す
- **debug 実行**: その場で渡す(1シナリオ・1台なので競合しない)
- **ロック以外の待ちとの組み合わせ**: クラスの `beforeAll` を他のデバイスが待つ門・割り振りの返事(`want`)の待ちは、どちらもロックを持たずに待つ
  (門はシナリオの開始時・`want` はシナリオの間)ので輪を作らない。ブロックの形なのでロックをシナリオの外へ持ち越せない

**利用者向け docs に書くこと**: ロックは「最初は1台で、のちに複数マシンへ」の移行で書き換えを要らなくするための簡易な仕組み。**他のテストの完了待ちに使わない**
(ロックを取り直して run メモを待つ書き方は、1台では配る順が早くて緑・複数台では相手が後回しになって時々赤になる)。重い排他・run をまたぐ排他は DB を使う。
入れ子は禁止なので要るキーは全部1回の呼び出しで渡す形を案内し、キーを実行時のデータで組み立てると名前の順がマシンごとに変わりうる(データセットの上書き)ことを書く。
激しい取り合いで待ちの上限に当たりうること・中断の後の片付けがロックで失敗しうること・振り直しで本体がもう一度走ることを書く。

確かめ方: 判定の型(規則①②・待ち行列・持ち主の終わり・持ち主不明・確かめ直し・取り消しと渡しのすれ違い)を単体テストで固定し、
規則を外す変異で落ちることを確かめる。接続の終わり・プロセスの死・転送の失敗は緑の run で通らないので注入する。陽性対照: 手元と M1Ultra にまたがる run で、
複数のテストが `withRunLock` の中で run メモのカウンタを足し、最後の値が**結果 JSON の実行回数**(振り直しを含む)と一致する・ロックを外した版では
一致しないこと(E2E-CMP だけに置く)

## RR-11 GUI(vscode-fleetest モニター)への影響

リモートデバイスをローカルと混在表示するときの契約。実装地点は RR-13「デバイスモニタータブの多ホスト監視」。

- **デバイスの識別に machine を含める**。デバイス名は全 Mac で衝突する(どのマシンにも「iPhone 17」がいる)ので、
  タイルは machine 別にグルーピングしてバッジを付ける。負荷チャートも machine 別の行に分ける
- **版ズレは実行前に聞く**: ランナーの更新は実行前の版ズレダイアログの「更新して実行」(= `fleetest remote align`。
  `vscode-fleetest/src/runHandler.ts`)。設定タブに「このホストを更新」の UI は無い
- **帯域**: リモートタイルの既定は低 FPS/静止サムネイル、**選択時のみライブ化**(可視タイルのみ配信)。
  H.264 全タイル常時配信は LAN 帯域で成立しない
- **フレーム経過秒をタイルに表示**する。「古いフレーム」の原因がデバイス凍結とネットワーク遅延の2値になり、
  表示なしでは切り分け不能
- **watchdog の分界**: 凍結検知は「フレーム不変=デバイス凍結」前提だが、リモートではリンク切れでも同じ見え方になる。
  **ホスト到達性を先に判定してからデバイス凍結と診断する**(入れないとネットワーク瞬断のたびに sleep/wake 修復が誤発火する)
- **run レーンにホスト帰属を表示**する(NDJSON にホストを乗せて流す)。罠: runLaneModel/runReducer は両バンドル共有 →
  新規表示文字列は `i18n/strings/lane.ts` のランタイム側(既存の i18n 制約)
- **占有の表示は「どの run が使用中か」まで**。「誰の」は出さない(RR-15.3 で同一信頼グループ限定を既定とした)
- **リモートへの `devices down` 相当は他人の run を殺し得る** → ホスト側 `showWarningMessage({modal:true})` で確認
  (webview の `window.confirm` は効かない)
- **レポート・録画リンクはクリック時に回収してから開く**(録画は大きいのでオンデマンド+withProgress)。
  実行ログは OUTPUT へ(ホスト別チャンネル or 行プレフィクス)
- **プロセスタブ・orphanSweep はローカルプロセス走査前提**でリモートに適用できない。リモート分は状態表示だけにし、
  効かない kill ボタンを出さない。掃除はリモート側 fleetest の責務
- **ライブ操作は他の機械のデバイスも開ける**(serve を向こうで起こす。`.claude/rules/live-control.md`)。
  watchdog の自動修復は発行側の拡張が ssh で撃つ(RR-13)
